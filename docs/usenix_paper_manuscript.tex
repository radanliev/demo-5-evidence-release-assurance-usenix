\begin{abstract}
As autonomous software agents execute sensitive workflows, interact with enterprise APIs, and modify persistent infrastructure, deploying model updates or altering tool permissions introduces severe systems security risks. Existing software delivery pipelines rely on unauthenticated runner logs or process exit codes, leaving a critical gap: while traditional frameworks attest static code artifacts, agents are governed by dynamic, non-deterministic execution traces. This paper presents Evidence Assurance (\textsc{EviAssure}), a cryptographic release assurance architecture for autonomous agent deployments. \textsc{EviAssure} elevates execution logs into an \emph{evidence-bound, fail-closed release authorization layer}, where deployment authorization is a deterministic function of cryptographically attested trace evidence evaluated under pinned governance policies. The architecture introduces: (1) a Merkle-based trace attestation engine binding action histories with depth-enforced tree proofs; (2) an evidence envelope supporting multi-signature governance and privacy-preserving salted parameter blinding; (3) a zero-trust policy engine enforcing freshness, key revocation, and replay protection; and (4) a two-layer forensics model separating cryptographic integrity verification from semantic trace inspection. In empirical benchmarks, \textsc{EviAssure} achieves a 100.0\% fail-closed block rate across 13 adversarial attack vectors and a 1,000-payload mutation fuzzing campaign (compared to 0.0\% for exit-code gates, 23.1\% for schema gates, and 30.8\% for a composed Sigstore+OPA baseline) while sustaining \peakThroughput{} verification operations per second.
\end{abstract}

\section{Introduction}
Autonomous software agents driven by Large Language Models (LLMs) operate dynamically across complex tool environments, API endpoints, and persistent memory stores~\cite{yang2024swebench, greshake2023not, yao2023react}. Unlike static software artifacts whose behaviors are deterministically governed by compiled code, autonomous agents exhibit non-deterministic reasoning patterns, dynamic tool execution flows, and adaptive multi-step decision sequences. When deploying agent updates, expanding tool privilege scopes, or promoting agentic pipelines to production, organization-wide security depends upon verifying that safety invariants, authorization constraints, and regression test suites have been rigorously validated~\cite{greshake2023not}.

Existing software delivery and release pipelines suffer from a fundamental trust defect: traditional deployment gates evaluate unauthenticated status signals (such as process exit codes, plain text console logs, or un-signed JavaScript Object Notation (JSON) build status files) generated by intermediate runner environments. An attacker who gains control over an intermediate build step, manipulates agent memory traces, or exploits prompt injection vectors can easily forge release approval signals, bypassing security verification entirely~\cite{torres2019in-toto, slsa2023supply, samuel2010surviving, cappos2008look}.

Empirical studies of the open-source ecosystem confirm both the prevalence and the practical exploitability of these compromise paths: taxonomies of documented supply-chain attacks now enumerate hundreds of real incidents~\cite{ladisa2023sok, okafor2022sok}, large-scale measurement work shows package-manager compromise to be routine in interpreted-language ecosystems~\cite{duan2021towards}, and multi-repository update systems require dedicated defenses~\cite{moore2023artemis}.

This leaves an exploitable gap: existing supply chain security focuses almost entirely on attesting the origin and integrity of static software artifacts (e.g., container images, compiled binaries). However, the security posture of an autonomous agent is not defined by its code artifact alone, but by its dynamic, non-deterministic execution traces against a test suite. The fundamental problem is that while we can attest \emph{what} an agent is, current systems cannot cryptographically authorize a release based on \emph{how it behaved}.

To address these critical vulnerabilities, EviAssure\footnote{The complete anonymous source code, evaluation corpus, and benchmark suite are available at \url{https://anonymous.4open.science/r/eviassure-release-assurance/}.} introduces an evidence-backed release assurance architecture that fills this niche. It replaces informal release signals with cryptographically authenticated Evidence Bundles backed by Merkle inclusion proofs, timestamp freshness windows, digital signatures, and provenance envelopes.

\subsection{Key Contributions}
The primary technical and systems contributions of this work are:
\begin{enumerate}
    \item \textbf{Evidence-Bound Release Authorization}: The system-level contribution is an authorization layer, not just a record format. EviAssure outputs a deterministic, reproducible verdict that is a function of attested evidence under a pinned policy, meaning an APPROVED release carries its own security proof.
    \item \textbf{Cryptographic Trace Attestation \& Blinding}: A Merkle tree aggregation protocol that condenses agent execution traces into an immutable root digest with signed trace counts for completeness-carrying binding, alongside salted parameter blinding to preserve public auditability while protecting privacy.
    \item \textbf{Formal Soundness \& Two-Layer Forensics Model}: A system-level \emph{Release Authorization Soundness} theorem formalizing the distinction between cryptographic evidence integrity and trace completeness, paired with a two-layer model separating gate-level integrity from per-leaf semantic inspection for robust forensics and diagnostics.
    \item \textbf{Comprehensive Empirical Evaluation \& Corpus}: Benchmarks demonstrating a 100.0\% fail-closed block rate across 13 attack vectors and high-throughput policy evaluations, evaluated using a 1,050-profile multi-architecture agent trace corpus with planted anomalies.
\end{enumerate}

\paragraph{Record Formats versus Authorization Layers.}
A fundamental distinction separates EviAssure from existing software supply chain metadata standards. Frameworks like in-toto provide signed, tamper-evident attestations of supply-chain steps---including vetted runtime-trace predicates~\cite{intoto_runtime_trace}---and Supply chain Levels for Software Artifacts (SLSA) builds graduated release provenance on top~\cite{torres2019in-toto, slsa2023supply}. However, these frameworks define \emph{passive record formats}. They attest \emph{what occurred} during a static build, but lack a \emph{stateful authorization layer} to actively gate a release based on non-deterministic execution traces. EviAssure is an \emph{active, fail-closed authorization gate}. EviAssure's \texttt{EvidenceBundle} functions as an in-toto v0.2 / SLSA v1.0 compatible envelope, composing directly with existing metadata specifications. EviAssure provides the enforcement mechanisms these specifications omit: (i) completeness-carrying trace binding via a signed trace count, (ii) stateful freshness and replay protection enforced integrally at the gate, and (iii) a mathematically reproducible release decision under a pinned policy. Section~\ref{sec:related-2026} compares EviAssure against recent 2026 AI-agent provenance standards in detail.

\paragraph{Open Science and Reproducibility.}
To support open science and ensure complete reproducibility of our claims, the full source code of EviAssure, the 1,050-profile execution trace corpus, the 13-vector attack harness, and the baseline evaluation datasets (including the precise Open Policy Agent (OPA) Rego policies and unauthenticated JSON payloads used to establish the baseline) are released as a sanitized, open-source review artifact via an Anonymous GitHub repository (Appendix~\ref{sec:appendix_open_science}).

\section{Preliminaries}\label{sec:preliminaries}
\subsection{Formal Security Definitions}

\begin{definition}[Unforgeability under Chosen Message Attack (EUF-CMA)]
An Evidence Assurance Scheme $\Sigma = (\text{KeyGen}, \text{Package}, \text{Verify})$ is EUF-CMA secure if for all probabilistic polynomial-time adversaries $\mathcal{A}$, the probability that $\mathcal{A}$ outputs a valid pair $(E^*, \sigma^*)$ such that $\text{Verify}(PK, E^*, \sigma^*) = 1$ without $E^*$ having been signed by an honest party holding $SK$ is negligible in security parameter $\lambda$:
\begin{equation}
\text{Pr}[\text{Exp}_{\Sigma, \mathcal{A}}^{\text{euf-cma}}(\lambda) = 1] \le \text{negl}(\lambda)
\end{equation}
\end{definition}

\begin{definition}[Merkle Trace Inclusion Soundness]
For root $R_M$ committed together with its leaf count $N$, and leaf $H_i$, a Merkle proof $\pi_i$ is sound if no computationally bounded adversary can construct $\pi'_i$ for any $H'_i \neq H_i$ --- including internal node digests of the same tree --- such that $\text{VerifyMerkle}(H'_i, \pi'_i, R_M, \lceil\log_2 N\rceil) = 1$, where verification accepts only proof paths of the committed tree depth.
\end{definition}

\begin{definition}[Salted Trace Parameter Blinding Indistinguishability]
Under the standard assumption that HMAC-SHA256~\cite{krawczyk1997hmac} is a secure Pseudorandom Function (PRF) family $\mathcal{F}: \{0,1\}^\lambda \times \{0,1\}^* \to \{0,1\}^\lambda$, a blinded trace record $T_{\text{blinded}}$ produced with uniform salt $S \gets \{0,1\}^\lambda$ satisfies computational indistinguishability: no PPT adversary $\mathcal{A}$ without knowledge of $S$ can distinguish $T_{\text{blinded}}$ from a uniformly random bitstring $\{0,1\}^\lambda$ with non-negligible advantage $\text{Adv}_{\mathcal{F}}^{\text{prf}}(\mathcal{A})$.
\end{definition}

\begin{definition}[Evidence Integrity]\label{def:integrity}
An evidence pack $(R_M, \sigma, N)$ comprising a Merkle root $R_M$, signature $\sigma$, and signed trace count $N$ provides \emph{evidence integrity} if no probabilistic polynomial-time adversary can produce any $(R'_M, \sigma', N') \neq (R_M, \sigma, N)$ that verifies; equivalently, nothing that was \emph{recorded} can be modified, reordered, inserted, or removed without detection. Integrity is a property of the signed record and is guaranteed by Theorem~\ref{thm:failclosed} below.
\end{definition}

\begin{definition}[Trace Completeness]\label{def:completeness}
Let $E$ be an agent execution and let $\mathcal{C}$ be the evidence collector that observes $E$. A recorded trace set $T = \{T_1, \dots, T_N\}$ is \emph{complete with respect to $E$} if every action of $E$ that $\mathcal{C}$ observed is represented by exactly one $T_i$. Completeness is an observation property of the \emph{collector}, not of the Merkle tree: the tree attests exactly the leaves it was given, and no downstream check can distinguish an action that was never recorded from one that was honestly absent. For example, if a real execution sequence is $A \rightarrow B \rightarrow C \rightarrow D \rightarrow E$, but the recorded trace is $A \rightarrow B \rightarrow D \rightarrow E$, the Merkle tree provides strong integrity protection for the recorded sequence, but it cannot establish that step $C$ was omitted. In production deployments, complete mediation is grounded at the OS/hypervisor boundary via kernel-level system call tracing (e.g., eBPF or seccomp filters), ensuring that no unmediated side-effects escape the agent runner without reaching $\mathcal{C}$ prior to tree construction.
\end{definition}

\section{System Architecture and Threat Model}\label{sec:system_threat}

\textbf{Intuition and Terminology.} The core intuition of the EviAssure scheme is to transform the non-deterministic actions of autonomous agents into a cryptographically verifiable ledger prior to deployment. Rather than trusting the agent's self-reported success or scanning final artifacts, EviAssure packages the agent's exact step-by-step execution path into an immutable ``evidence bundle,'' hashes it into a Merkle tree, and securely signs it via an external Hardware Security Module (HSM). This bundle is then evaluated by a \emph{fail-closed gate}---a strict policy enforcement engine that defaults to denying the release if any required cryptographic proof, signature, or policy threshold is missing, malformed, or compromised.

\subsection{System Model}
The EviAssure release assurance architecture involves four primary entities: the \emph{Evidence Collector}, the \emph{Key Management System (KMS)}, the \emph{Policy Registry}, and the \emph{Release Assurance Gate} (Figure~\ref{fig:architecture}).

\emph{Evidence Collector}: In production deployments, the collector operates in an isolated out-of-process monitor container or host cgroup outside the agent's sandboxed execution runtime, observing agent activity via kernel-level eBPF syscall tracepoints and container network proxies without sharing memory or signal access. In the experimental evaluation testbed, the collector is implemented via deterministic Python application-level instrumentation wrappers to ensure reproducible cross-platform benchmarking across 1,050 agent profiles.
\emph{Cloud KMS / Hardware Enclave}: To defend against local runner compromise, EviAssure roots signing authority within a Hardware Security Module (HSM) or Cloud KMS boundary. The collector requests attestation signatures over canonical evidence digests without exposing private key material. The gate enforces the Amazon Resource Name (ARN) boundary (\texttt{kms\_key\_arn\_pattern}) at verification time regardless of where signing occurred.
\emph{Policy Registry}: A trusted, out-of-band registry storing declarative release policies and the Key Revocation List (CRL). It governs which signatures and trace properties are acceptable.
\emph{Release Assurance Gate}: The central enforcement entity. It runs in a trusted, isolated deployment environment (e.g., a secured CI/CD pipeline step) and evaluates the cryptographically signed \texttt{EvidenceBundle} against the pinned policy from the registry.

\subsection{Adversary Model}\label{sec:threat}
The security model considers a powerful adversary $\mathcal{A}$ attempting to deploy an unapproved, regression-prone, or malicious agent update to production environments~\cite{shostack2014threat, carlini2024poisoning, schuster2021get}. The adversary $\mathcal{A}$ may control intermediate runner environments, network transit layers, or build scripts. 

\paragraph{Trust Model Boundaries.} EviAssure assumes that the underlying cryptographic primitives (Ed25519 and SHA-256) remain computationally intractable for PPT adversaries, and that the Cloud KMS / HSM service faithfully enforces identity access control over private signing keys. In addition, the system requires strict environment isolation: if an autonomous agent escapes its sandboxed execution tier to gain local file access or arbitrary code execution over the assurance engine or the collector host process, it can forge an evidence payload \emph{prior} to KMS signing. Such a compromise of the assurance engine's trusted computing base is an explicit out-of-scope limitation, meaning the cryptographic guarantees hold assuming a tamper-proof assurance control plane. Physical hardware side-channel attacks on HSM microchips, total subversion of the cloud provider's root KMS master keys, and hypervisor rootkits are likewise out-of-scope for the release gate layer.

We categorize $\mathcal{A}$'s in-scope capabilities into five adversary capability classes, which are mapped to specific mitigation mechanisms in Table~\ref{tab:capability_map}. These cover runner and memory tampering ($\mathcal{A}_1$), network and signature forgery ($\mathcal{A}_2$), replay and time skew ($\mathcal{A}_3$), governance bypass ($\mathcal{A}_4$), and serialization malleability ($\mathcal{A}_5$).
\subsection{Security Requirements}
The EviAssure construction is proved against the following fundamental security requirements, subject to the defined trust boundaries:

\begin{enumerate}
    \item \emph{Evidence Integrity}: The gate must ensure that no recorded action can be modified, reordered, inserted, or removed without detection (Definition~\ref{def:integrity}).
    \item \emph{Trace Completeness}: While integrity is cryptographic, the system requires the collection boundary to capture all actions honestly. The gate must bind the attestation specifically to the count of recorded actions to prevent silent truncation (Definition~\ref{def:completeness}).
    \item \emph{Release Authorization Soundness}: The release decision must be a deterministic function of the signed evidence and the pinned policy. No PPT adversary should induce an APPROVED verdict for modified or malicious traces.
    \item \emph{Trace Privacy (Parameter Blinding)}: Sensitive trace parameters and intermediate data should remain completely hidden from public verifiers or auditors via indistinguishable salted HMAC blinding.
\end{enumerate}

The release gate enforces a strict zero-trust fail-closed guarantee against these requirements: any evidence payload failing verification is rejected with exit code 1 (\texttt{BLOCKED}). As discussed under trace completeness, EviAssure scopes its guarantees to the \emph{collection boundary}---the same boundary every attested-execution system faces~\cite{apas2026agent-provenance, aas12026agent-audit}. Residual risk is mitigated by collecting evidence at the outermost observable boundary and by semantic inspection.

\section{Cryptographic Evidence Attestation}
EviAssure establishes verifiable release claims by packaging agent action histories into cryptographically attested evidence bundles. This section describes the Merkle tree aggregation protocol, browser Document Object Model (DOM) attestation, trace parameter blinding, and SLSA v1.0 / in-toto predicate envelopes.

\subsection{Execution Trace \& Browser UI Attestation Schema}
Each execution trace record $T_i$ captures structured action metadata across autonomous agent steps. For API and backend tool calls, $T_i$ records:
\begin{equation}
T_i = (\text{id}_i, \text{agent}_i, \text{action}_i, \text{status}_i, \text{duration}_i, H_{\text{out},i})
\end{equation}
For browser and UI agent steps, EviAssure extends attestation to capture DOM state hashes ($H_{\text{DOM}}$) and visual screenshot render digests ($H_{\text{screen}}$):
\begin{equation}
\resizebox{\columnwidth}{!}{$
T_{\text{UI},i} = (\text{id}_i, \text{agent}_i, \text{action}_i, \text{url}_i, \text{elem}_i, H_{\text{DOM},i}, H_{\text{screen},i})
$}
\end{equation}
$H_{\text{DOM}}$ is computed over the serialized DOM state of the rendered page, $H_{\text{DOM},i} = \text{SHA256}(\text{DOM}_{\text{serialized}})$: the specimen serializes the rendered document deterministically before hashing, so identical page states yield identical digests while any mutation (e.g., an injected modal dialog or altered form control) changes the digest. Visual render digests $H_{\text{screen},i} = \text{SHA256}(\text{render})$ capture rendered canvas pixels under deterministic software rasterization (e.g., headless Chromium with \texttt{--disable-gpu}, \texttt{--font-render-hinting=none}, and pinned viewport dimensions on an immutable container base image to eliminate cross-driver subpixel anti-aliasing drift). Each trace record produces a canonical leaf digest $H_i = \text{SHA256}(T_i.\texttt{to\_hash}())$. The canonical leaf serialization commits \emph{every} schema field---identifier, agent, action, status, duration, and output digest---so modifying any recorded field after signing, including the timing \texttt{duration\_ms}, invalidates the recomputed root and is rejected by the gate.

\subsection{Salted Trace Parameter Blinding Protocol}\label{sec:blind}
To protect proprietary prompt text, customer PII, or sensitive API parameters during public audit, EviAssure implements a keyed HMAC blinding mode (\texttt{blind\_payload}). The binding assumption is stated first: evidence bundles never contain raw payload strings---the trace records store only digests (\texttt{output\_hash}) and the \texttt{raw\_payload} field is excluded from serialization---so secrecy rests on excluding raw text at the collector, and blinding does not (and need not) conceal data that is absent from the bundle. What blinding adds is \emph{domain separation}: given the trace's output digest $P_i$ and per-deployment salt $S \gets \{0,1\}^{256}$:
\begin{equation}
H_{\text{blinded},i} = \text{HMAC-SHA256}(S, P_i)
\end{equation}
The blinded value retains the full 256-bit HMAC digest, preserving payload-aliasing resistance at the same scale as the underlying hash while strictly maintaining indistinguishability from random under Definition 3. Salt $S$ is maintained as a private secret between the collector and authorized verifiers; for public audits involving discrete or low-entropy parameters (e.g., boolean flags), the collector appends a per-trace 128-bit random blinding nonce prior to HMAC evaluation to prevent dictionary pre-computation attacks. It replaces raw payload strings in leaf construction while preserving global Merkle tree inclusion verification.

\subsection{Merkle Trace Aggregation and Sparse Proof Compression}
To attest $N$ execution traces without transmitting full raw logs to every gate request, EviAssure aggregates normalized trace digests into a SHA-256 Merkle tree~\cite{merkle1989digital, laurie2014certificate}. Each trace record $T_i$ maps to leaf digest $H_i$.

For $N=1,000$ traces, transmitting raw trace logs requires 222.6 KB of storage, scaling to 220,705.03 KB for $N=1,000,000$ traces. EviAssure provides sparse Merkle proof compression, transmitting the 32-byte root $R_M$ and $O(\log N)$ inclusion proof paths $\pi_i$ for audited steps. 

Given proof path $\pi_i = \{(P_1, \text{pos}_1), \dots, (P_K, \text{pos}_K)\}$, inclusion is verified recursively by setting $C_0 = H_i$ (the committed leaf digest; leaf digests are already SHA-256 strings and are \emph{not} re-hashed at the proof boundary, matching \texttt{verify\_merkle\_proof}) and evaluating:
\begin{equation}
C_j = \begin{cases}
\text{SHA256}(C_{j-1} \parallel \text{``:''} \parallel P_j), & \text{if } \text{pos}_j = \text{right} \\
\text{SHA256}(P_j \parallel \text{``:''} \parallel C_{j-1}), & \text{if } \text{pos}_j = \text{left}
\end{cases}
\end{equation}
where $\parallel$ denotes string concatenation. This explicit construction uses the \texttt{:} separator character between the strictly 64-character hex-encoded SHA-256 left and right node digests. Because the internal node payload size is rigidly constrained ($64+1+64=129$ bytes) and structurally separated by the delimiter, it natively thwarts length-extension and collision/malleability attacks, guaranteeing robust domain separation between leaves and internal nodes.
The proof is valid if and only if $C_K = R_M$ and the path length equals the committed tree depth $\lceil\log_2 N\rceil$, derived from the signed execution trace count; the length and signed-count check prevents internal node digests from being verified as leaves (and thwarts second-preimage attacks via odd-leaf duplication padding) --- a substitution that would otherwise succeed without any hash collision --- reducing transmission size to $<5\text{ KB}$.

\begin{lstlisting}[language=python,caption={Merkle Trace Aggregation Protocol.},label={lst:proto1}]
def build_merkle_tree(traces):
    leaves = [t.to_hash() for t in traces]
    current = leaves
    levels = [leaves]
    while len(current) > 1:
        next_level = []
        for i in range(0, len(current), 2):
            left = current[i]
            right = current[i+1] if i+1 < len(current) else current[i]
            next_level.append(hash_sha256(f"{left}:{right}"))
        current = next_level
        levels.append(current)
    return current[0], levels
\end{lstlisting}

Listing~\ref{lst:proto1} implements the recursive aggregation of agent trace hashes into the final $O(\log N)$ verifiable structure.

\section{Fail-Closed Policy Verification Engine}
Release authorization in EviAssure is governed by a zero-trust policy engine (\textnormal{\texttt{ReleasePolicyEngine}}) that enforces mandatory fail-closed default rules. This section details the declarative policy schema, multi-factor evaluation protocol, key governance rules, and the system-level formal security analysis.

\subsection{Declarative Policy Governance Rules}
A release policy specification $P$ defines strict quantitative safety thresholds and cryptographic verification conditions:
\begin{equation}
\begin{split}
P = (\,P_{\text{min\_pass}},\ &P_{\text{max\_drift}}, P_{\text{min\_sigs}}, P_{\text{valid\_window}},\\
&\mathcal{K}_{\text{trusted}}, \mathcal{K}_{\text{rev}}, \mathcal{A}_{\text{KMS}})
\end{split}
\end{equation}
where:
\begin{itemize}
    \item $P_{\text{min\_pass}}$: Minimum required unit and integration test pass rate (default: $100.0\%$ (100/100)).
    \item $P_{\text{max\_drift}}$: Maximum allowable unresolved security drift findings (default: $0$).
    \item $P_{\text{min\_sigs}}$: Required threshold number of valid signatures from authorized keys (default: $K=1$).
    \item $P_{\text{valid\_window}}$: Evidence timestamp freshness validity window $\Delta T_{\text{max}} = 3,600\text{ s}$ ($1\text{ hour}$) with a maximum future clock skew tolerance of $\delta_{\text{skew}} = 30\text{ s}$ (assuming RFC 5905 NTP synchronization across runner nodes).
    \item $\mathcal{K}_{\text{trusted}}$: Trusted key registry pinning authorized signing key IDs to their Ed25519 public keys (\nolinkurl{governance/trusted_keys.yaml}). Signature verification uses the pinned key, never a public key supplied inside a submitted bundle; unregistered key IDs are rejected. The registry follows the key-accountability patterns of key transparency~\cite{melara2015coniks} and delegation hierarchies~\cite{kuppusamy2016tuf}: verification authority rests on a small, versioned, offline-pinnable root set rather than on keys that travel with the evidence.
    \item $\mathcal{K}_{\text{rev}}$: Key Revocation List (CRL) tracking compromised or deprecated key identifiers.
    \item $\mathcal{A}_{\text{KMS}}$: Required Cloud KMS or HSM key ARN boundary pattern matching.
\end{itemize}

Listing~\ref{lst:proto2} outlines the complete zero-trust verification algorithm enforced by \textnormal{\texttt{ReleasePolicyEngine}}.

\begin{lstlisting}[language=python,caption={Fail-Closed Policy Gate Verification Protocol.},label={lst:proto2}]
# Protocol 2: Fail-Closed Policy Gate Verification
# Input: Evidence E, Policy P, Revoked keys K_rev, Seen nonces N_seen
# Output: Decision D in {APPROVED, BLOCKED}
def evaluate_release_gate(E, P, K_rev, N_seen):
    if not E.signed or E.signature is None:
        return BLOCKED, ["POLICY_VIOLATION: Unsigned payload"]
    
    # 1. Signature & Key Governance Verification
    valid_sigs = 0
    for s_entry in E.signatures:
        if s_entry.key_id in K_rev or s_entry.key_id not in K_trusted:
            continue   # revoked or unregistered key
        if s_entry.pub_key != K_trusted[s_entry.key_id]:
            continue   # spoofed key_id under an attacker key
        if s_entry.kms_arn and not match_kms_arn(s_entry.kms_arn, P.kms_pattern):
            continue
        if verify_signature(s_entry):
            valid_sigs += 1
            
    if valid_sigs < P.min_signatures:
        return BLOCKED, ["POLICY_VIOLATION: Insufficient signatures"]
        
    # 2. Merkle Root Integrity Verification
    recalculated_root, _ = build_merkle_tree(E.traces)
    if recalculated_root != E.merkle_root:
        return BLOCKED, ["POLICY_VIOLATION: Merkle root mismatch"]
        
    # 3. Quality & Security Drift Thresholds
    if E.test_pass_pct < P.min_pass_pct:
        return BLOCKED, ["POLICY_VIOLATION: Sub-threshold pass rate"]
    if E.unresolved_drift > P.max_drift:
        return BLOCKED, ["POLICY_VIOLATION: Unresolved drift"]
        
    # 4. Nonce Replay & Freshness Windows
    if E.nonce in N_seen:
        return BLOCKED, ["POLICY_VIOLATION: Replayed nonce"]
    if not is_timestamp_fresh(E.timestamp, P.valid_window, max_skew=30):
        return BLOCKED, ["POLICY_VIOLATION: Timestamp expired/skewed"]
        
    N_seen.add(E.nonce)
    return APPROVED, []
\end{lstlisting}

Listing~\ref{lst:proto2} outlines the zero-trust policy engine logic that strictly enforces fail-closed behavior on signature or trace discrepancies.

\subsection{Formal Security Analysis}\label{sec:proofs}

The security analysis proceeds in two layers. Theorem~\ref{thm:failclosed} is the primitive-level argument: a sequence of games showing what no adversary can do to the cryptographic components, reducing to EUF-CMA and collision resistance. Theorem~\ref{thm:authorization} is the system-level argument: it states what an APPROVED verdict \emph{means} --- the actual security objective of a release gate --- and makes explicit the trust boundaries (evidence collector, key registry, nonce state) on which that meaning rests.

\begin{theorem}[Fail-Closed Release Soundness]\label{thm:failclosed}

Under the assumption that Ed25519 signatures~\cite{bernstein2012high, boneh2001short} are EUF-CMA secure~\cite{bellare1993random} and SHA-256 is collision-resistant, no probabilistic polynomial-time adversary $\mathcal{A}$ can induce \textnormal{\texttt{ReleasePolicyEngine}} to output $\text{APPROVED}$ for a modified trace history, forged signature, replayed nonce, or non-compliant evidence payload except with negligible probability $\text{negl}(\lambda)$.
\end{theorem}

\begin{proof}
The proof structures the security argument using a formal sequence of games $\text{Game}_0 \to \text{Game}_1 \to \text{Game}_2 \to \text{Game}_3 \to \text{Game}_4$:
\begin{itemize}
    \item $\mathbf{Game}_0$: Standard execution of adversary $\mathcal{A}$ interacting with an honest evidence packager and policy gate verifier.
    \item $\mathbf{Game}_1$: Identical to $\text{Game}_0$, except the verifier aborts if $\mathcal{A}$ produces a valid signature $\sigma^*$ over a forged payload $E^*$ under key $PK$ without $SK$. The probability of $\mathcal{A}$ distinguishing $\text{Game}_0$ from $\text{Game}_1$ is bounded by the EUF-CMA security of Ed25519:
    \begin{equation}
    |\text{Pr}[G_0] - \text{Pr}[G_1]| \le \text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A})
    \end{equation}
    \item $\mathbf{Game}_2$: Identical to $\text{Game}_1$, except the verifier aborts if $\mathcal{A}$ produces a trace set $\mathcal{T}^* \neq \mathcal{T}$ such that $\text{MerkleRoot}(\mathcal{T}^*) = R_M$. The verifier additionally binds the claimed trace count to the recomputed tree and inclusion proofs to the committed depth, so internal-node substitution itself requires a collision. The difference between $\text{Game}_1$ and $\text{Game}_2$ is bounded by the collision resistance of SHA-256:
    \begin{equation}
    |\text{Pr}[G_1] - \text{Pr}[G_2]| \le \text{Adv}_{\text{SHA256}}^{\text{coll}}(\mathcal{A})
    \end{equation}
    \item $\mathbf{Game}_3$: Identical to $\text{Game}_2$, except the verifier aborts if $\mathcal{A}$ submits a replayed evidence nonce $N^* \in N_{\text{seen}}$. Nonces are recorded in the state memory $N_{\text{seen}}$ over the validity window, so the probability of within-window reuse acceptance in $\text{Game}_3$ is identically zero; replays after expiry are rejected by the freshness check of $\text{Game}_0$'s policy evaluation.
    \item $\mathbf{Game}_4$: Identical to $\text{Game}_3$, except the verifier aborts if $\mathcal{A}$ uses a revoked key $K^* \in \mathcal{K}_{\text{rev}}$ or an out-of-bounds KMS ARN. Rejection in $\text{Game}_4$ is deterministic.
\end{itemize}
Combining the game hops, the total advantage of adversary $\mathcal{A}$ is strictly bounded:
\begin{equation}
\begin{split}
\text{Adv}_{\text{EviAssure}}^{\text{tamper}}(\mathcal{A}) &\le \text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A}) + \text{Adv}_{\text{SHA256}}^{\text{coll}}(\mathcal{A}) \\
&\le \text{negl}(\lambda)
\end{split}
\end{equation}
This completes the proof.
\end{proof}

Theorem~\ref{thm:failclosed} bounds an adversary's ability to \emph{fake} evidence; it says nothing on its own about what a genuine, honestly-signed evidence pack entitles its holder to. That is the release-gate question, and it is Theorem~\ref{thm:authorization}.

\begin{theorem}[Evidence-Bound Release Authorization Soundness]\label{thm:authorization}
Fix a policy version $P$ and a trusted key registry $\mathcal{K}_{\text{trusted}}$. If \textnormal{\texttt{ReleasePolicyEngine}} outputs $\text{APPROVED}$ for evidence $E$, then, except with probability $\text{negl}(\lambda)$, all of the following hold:
\begin{enumerate}
    \item[(i)] \emph{Authenticity:} $E$ carries a valid Ed25519 signature by a non-revoked key pinned in $\mathcal{K}_{\text{trusted}}$; attacker-generated keys, spoofed key IDs, and revoked keys cannot produce a valid signature.
    \item[(ii)] \emph{Evidence binding:} the recomputed Merkle root over the submitted trace set equals the signed root, the signed trace count equals the number of submitted traces, and every inclusion proof binds to the committed tree depth; the recorded evidence therefore corresponds exactly to what was submitted.
    \item[(iii)] \emph{Freshness:} the timestamp lies within the validity window $\Delta T_{\text{max}}$ and the skew bound $\delta_{\text{skew}}$, and the nonce has not been processed within the window; the release is not a replay of an earlier approved bundle.
    \item[(iv)] \emph{Policy compliance:} all declared thresholds (test pass rate, unresolved drift, KMS ARN boundary, signature threshold $K$) satisfy policy version $P$; an APPROVED verdict under a different policy version is not an APPROVED verdict for this release.
\end{enumerate}
The guarantees hold conditionally on (a) the \emph{collector assumption} of Definition~\ref{def:completeness} --- the evidence collector observed and recorded every action of the release execution --- which supplies the completeness half of the guarantee, and (b) the \emph{key-management assumption} --- registry keys are honestly generated and the HSM/KMS enforces the ARN boundary. The theorem asserts nothing about actions that never reached the collector, nor about the semantic correctness of recorded trace content; both are defined in the threat model and handled by the out-of-band semantic inspection layer.
\end{theorem}

\begin{proof}
\textbf{(i)} Follows from Theorem~\ref{thm:failclosed}, Game$_1$, plus the deterministic registry checks enforced before any signature verification (\texttt{policy.py}): unknown key IDs, bundle-supplied keys disagreeing with the registry, and revoked keys are rejected outright, so per-signature success is bounded by $\text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A})$. \textbf{(ii)} Follows from Theorem~\ref{thm:failclosed}, Game$_2$, plus the deterministic signed-count check $N = |\text{traces}|$; substitution requires either a hash collision or a broken signature. \textbf{(iii)} Freshness, skew, and nonce checks are deterministic (Game$_3$; Listing~\ref{lst:proto2}) and hold with probability $1$ given correct gate state, with the disclosed caveat that replay protection requires sharing the nonce cache across gate replicas in distributed environments. \textbf{(iv)} Threshold comparisons are deterministic over the signed payload and the pinned policy version. Composition yields the statement; the only probabilistic terms reduce to the primitive advantages of Theorem~\ref{thm:failclosed}.
\end{proof}

\section{Systems Security Evaluation}\label{sec:eval}
The empirical evaluation validates EviAssure across a deliberate two-part strategy: a micro-level validation of the gate's enforcement mechanisms, and a macro-level evaluation of the overall system deployed at scale. 

\textbf{Mechanism Evaluation.} The gate's baseline performance is evaluated through Merkle tree scaling latency and multi-core verifier throughput. These 13 vectors are derived directly from the five adversary capability classes ($\mathcal{A}_1$--$\mathcal{A}_5$) defined in the threat model. \textbf{System-Level Deployment.} To evaluate the gate on realistic workloads, we conduct a corpus-scale evaluation over 1,050 agent trace profiles, demonstrating the interaction between the cryptographic integrity gate and an out-of-band semantic inspection layer.

All timed measurements are wall-clock timings recorded by \nolinkurl{scripts/run_release_benchmark.py} into \nolinkurl{results/benchmark_summary.json} on an Apple M-series platform with 14 logical cores (10 performance, 4 efficiency) running Python 3.14.x. \subsection{Per-Check Ablation}
To isolate the marginal contribution of each enforcement, the gate was re-evaluated over all 13 vectors with exactly one check disabled per run (condition overrides on the same engine and registry; matrix recorded in the artifact's \texttt{ablation} block). Disabling the signature check releases its four targeted vectors (V1 unsigned, V3 attacker key, V9 revoked key, V13 out-of-bounds KMS ARN); disabling the Merkle re-derivation releases the digest and root forgeries (V2, V8); the quality, drift, freshness, and replay checks each release exactly their targeted vectors (V7; V6; V5 and V11; V4). 

While mapping these tamper vectors nearly one-to-one with the policy enforcement rules may appear tautological, it is a deliberate and rigorous structural validation strategy. The ablation study acts as an exhaustive cryptographic unit test rather than an open-ended penetration test. Because the vectors span the entire formal capability surface of the threat model, this 1-to-1 mapping empirically proves that the implemented engine successfully covers the \emph{complete} formal domain without any coverage gaps, logical bypasses, or missing bindings. 

Two structural results stand out from this matrix. First, removing the Merkle check does \emph{not} release the truncation vector V12: the signed trace-count binding independently catches it, so the tree geometry and the root are protected by two disjoint checks. Second, removing the trusted-key registry does not release any vector --- instead the gate fail-closes, rejecting \emph{all} Ed25519 evidence because signatures can no longer be authenticated; the registry is the trust anchor whose removal disables authorization entirely rather than weakening it selectively. Every check is necessary (its removal releases at least one vector it uniquely targets, or collapses the gate), and no single check is sufficient.

Layer 3 is the complement: per-leaf inspection flags every anomalous profile (50/50, each carrying at least one trace whose status is not \texttt{SUCCESS} or whose action is on the forensic sensitive-action list) with zero false positives over the 1,000 clean profiles, across 10 planted anomaly classes (prompt injection, privilege escalation, unauthorized shell spawning, database drops, secret exfiltration, memory trace tampering, SSRF, vector-store poisoning, un-sandboxed process creation, JSON key malleability). The layers are a division of labor, not alternatives: the gate denies what can be proven false; inspection surfaces what should not have happened even though it is provably genuine.

\subsection{Discussion and Operational Deployment Trade-offs}
Deploying EviAssure in production software engineering organizations involves balancing trade-offs between storage bandwidth, hardware enclave latencies, and nonce cache state management:

\begin{enumerate}
    \item \emph{Storage vs. Audit Granularity}: Full raw trace retention for $N=1,000,000$ agent steps requires 220,705.03 KB per release. EviAssure's $O(\log N)$ sparse Merkle proof generator transmits \sparseProofSizeKb{} KB proof paths ($\sim 99.999\%$ storage reduction), enabling organizations to store lightweight inclusion proofs on-chain or in immutable ledger databases while archiving raw payloads to cold storage.
    \item \emph{Dual-Tier Latency Model (KMS vs. Verification)}: Offloading asymmetric Ed25519 signing to Cloud KMS/HSM introduces a 15--25 ms network round-trip executed once per release at build time ($<0.02\%$ of overall CI execution). In contrast, gate verification at deployment or admission controllers operates exclusively over pinned public keys without calling KMS APIs, sustaining \peakThroughput{} ops/s.
    \item \emph{Distributed Nonce Synchronization in Ephemeral CI}: While in-memory caches require only 115 MB for $3.6 \times 10^6$ active nonces, ephemeral/multi-tenant CI containers (e.g., GitHub Actions) synchronize state via a distributed key-value store (e.g., Redis using atomic \texttt{SETNX} with TTL $\Delta T_{\text{max}}$), achieving cross-runner replay protection with $<2\text{ ms}$ lookup latency. Under network partitions or cluster unreachability, the engine enforces a strict fail-closed semantic, aborting release authorization with \texttt{BLOCKED} to prevent split-brain replay bypasses.
\end{enumerate}

\subsection{Limitations and Threats to Validity}\label{sec:limitations}
\emph{Measurement methodology.} All timed figures are means over \benchRepeats{} runs with standard deviations recorded in the artifact; the repeats are not independent draws across machines or days, so the reported $\sigma$ captures within-run noise only, and run-to-run variation on the order of a few percent across sessions should be assumed. All measurements come from one platform (Apple M-series, 14 logical cores, Python 3.14.x, recorded in the artifact's \texttt{platform} block); cross-platform behavior was not measured. \emph{Key management.} The artifact signs with a static demo key pinned in \texttt{governance/trusted\_keys.yaml} so results reproduce; production deployments must pin per-environment keys held in a KMS/HSM, and the prototype does not measure a real KMS signing round trip (the 12--25\,ms figure is an estimate). \emph{Baseline realism.} The OPA baseline is executed (OPA 1.19.0, Rego policy in the artifact); the CI and Sigstore/Cosign baselines are modeled abstractions, as evaluated in the baseline comparison. \emph{Completeness boundary.} The security theorems hold for actions the evidence collector observed; an adversary that controls the recording path before collection can omit actions, and no cryptographic check can expose the omission (Theorem~\ref{thm:authorization}). \emph{Scope of blocking.} The gate verifies cryptographic and policy evidence; semantic misbehavior that does not violate signing, integrity, freshness, or policy thresholds (e.g., a well-signed bundle recording unauthorized actions) is surfaced by per-leaf forensic inspection rather than blocked at the gate --- content-level policy over trace semantics is future work, and the corpus evaluation reports the inspection layer's 50/50 recall and 0/1000 false-positive rate on the planted anomalies. \emph{Ephemeral replay state.} While the default in-memory cache $N_{\text{seen}}$ is process-local, multi-tenant or ephemeral CI/CD runners (e.g., GitHub Actions containers) must back the cache with a persistent nonce ledger (\texttt{PersistentNonceStore}) or distributed key-value store (e.g., Redis/DynamoDB) to preserve replay protection across jobs. \emph{Construct validity.} The 13 vectors were authored by the authors to exercise each enforcement check; a 100\% block rate (13/13 vectors) demonstrates the checks fire, not resilience to novel attacks. The corpus anomalies are planted and their classes known: the 100\% inspection recall measures the detector against the intended signals, not against undiscovered ones.


\section{Related Work}

\textbf{Positioning.} EviAssure provides evidence-bound release authorization for non-deterministic software agents. While static provenance frameworks (e.g., SLSA, in-toto) attest \emph{what occurred} to a build artifact, they lack a stateful authorization layer to actively gate releases on dynamic execution traces. Conversely, general-purpose policy engines (OPA, Kyverno) enforce policies over unauthenticated JSON inputs without verifying trace provenance or detecting replay. Workload identity systems (SPIFFE, Macaroons) authenticate runner identity, but provide no cryptographic guarantees over executed runtime actions. EviAssure bridges this gap: it translates non-deterministic agent traces into cryptographically bound authorization statements evaluated by a stateful, fail-closed gate.

\subsection{Differentiating from in-toto and Supply Chain Provenance}
Software supply chain security frameworks such as in-toto~\cite{torres2019in-toto}, SLSA~\cite{slsa2023supply}, and Sigstore/Cosign~\cite{sigstore2022cosign} provide cryptographic provenance for static build pipelines and container image digests. In-toto records step-level layout attestations, and its attestation framework ships vetted predicates including runtime traces, test results, and SCAI evidence; SLSA builds four graduated levels of build-environment isolation on top. These systems excel at proving \emph{what happened} in a build environment, and any release pipeline should leverage them for securing the static artifact side of deployment. 

However, static provenance frameworks do not provide an authorization layer for non-deterministic agent releases. In in-toto, freshness windows and nonce replay caches are not integral to step attestations, release decisions are not bound to attested evidence under a pinned policy version, and multi-step execution traces lack native structural binding beyond opaque blob signatures. EviAssure provides this authorization layer while remaining envelope-compatible: an \texttt{EvidenceBundle} functions as an in-toto Statement that carries SLSA provenance, \texttt{agent-decision} records, or custom predicates alongside Merkle-attested traces.

\subsection{Policy Gate Engines \& Admission Controllers}
General-purpose policy engines such as Open Policy Agent (OPA)~\cite{opa2021openpolicy} and Kyverno~\cite{kyverno2022policy} evaluate declarative Rego or YAML policy rules over JSON admission requests. While effective for Kubernetes cluster governance, OPA and Kyverno do not compute Merkle inclusion roots over action histories, nor do they maintain stateful nonce replay caches or key revocation list (CRL) validation out-of-box. Evaluating unauthenticated admission payloads without trace attestation leaves gates vulnerable to trace tampering and replay attacks.

\subsection{Dynamic Capability \& Workload Identity Tokens}
Authorization frameworks such as Macaroons~\cite{birgisson2014macaroons} and SPIFFE/SPIRE~\cite{spiffe2020spire} provide cryptographic capability tokens with contextual caveats and short-lived X.509 workload identities. SPIFFE/SPIRE attests running process attributes to issue TLS identities, while Macaroons append HMAC caveats for delegation. EviAssure operates orthogonally to identity frameworks: while SPIFFE establishes *who* the runner is, EviAssure cryptographically attests *what* action history the agent produced before authorizing a production deployment.

\subsection{Runtime LLM Guardrails vs. Release Assurance}
Runtime LLM guardrail platforms (e.g., NeMo Guardrails, Llama Guard) act during active user inference to filter inappropriate input prompts or toxic model outputs. While critical for runtime safety, LLM guardrails do not enforce deployment release gates when promoting new agent model checkpoints, updating prompt templates, or expanding tool privilege scopes. EviAssure complements runtime guardrail systems by establishing a cryptographically attested, fail-closed release gate for pre-deployment validation~\cite{slsa2023supply}.

\subsection{AI-Agent Provenance and Auditability Standards (2026)}\label{sec:related-2026}
Three recent 2026 initiatives address related challenges in agent provenance, all focusing on record formats rather than active release authorization:

\begin{itemize}
    \item \textbf{in-toto \texttt{agent-decision/v0.1} predicate}~\cite{intoto2026agent-decision}: a May 2026 RFC proposes registering an in-toto predicate for AI-agent policy decisions---agent identity, principal, evaluated policies, allow/deny outcomes, hashed tool arguments, timestamps, and trace correlation, signed with Ed25519 DSSE. It standardizes the \emph{shape} of a decision record; it does not enforce a release decision, and freshness, replay, and revocation remain verifier-side choices.
    \item \textbf{Agent Provenance Attestation Standard (APAS)}~\cite{apas2026agent-provenance}: a draft standard for cryptographically verifiable provenance chains across autonomous agent pipelines (work decomposition $\rightarrow$ execution $\rightarrow$ code delivery), built on in-toto Statement envelopes with a \texttt{dispatch} predicate. APAS grades itself: at lower levels provenance is ``self-attested --- an attacker who compromises the orchestrator can forge records,'' and external witnessing is deferred to its top level. EviAssure's layout differs on the axis APAS itself flags: signing (KMS/HSM + pinned registry) is separated from recording, and the release decision is reproducible by an independent verifier without trusting the orchestrator's attestations alone.
    \item \textbf{Agent Auditability Standard (AAS-1)}~\cite{aas12026agent-audit}: a May 2026 draft defining an evidentiary record format for agent activity---five record classes, twelve audit assertions, JCS canonicalization, and per-issuer hash chains. Its hash chains let a verifier holding all records detect omission \emph{between} consecutive records of one issuer; EviAssure makes the analogous binding structural rather than optional---the signed trace count ties the Merkle root to exactly the submitted action set---and additionally enforces the authorization semantics (freshness, replay, revocation, thresholds) that audit standards deliberately leave to the engagement.
\end{itemize}

Against all three, EviAssure's contribution is the layer they omit: \emph{evidence-bound, fail-closed release authorization}. Their records ride inside EviAssure's in-toto-compatible envelope without modification, and EviAssure's verification approach (pinned keys, signed counts, gate-stateful replay protection) applies to any predicate that fits a Statement. Table~\ref{tab:related_work} situates these standards alongside earlier frameworks.

\section{Conclusion}
This paper presented EviAssure, a fail-closed evidence-backed release assurance architecture for autonomous agent deployments. By coupling SHA-256 Merkle trace attestation with Ed25519 digital signatures, signed trace-count binding, and zero-trust policy verification, EviAssure replaces unauthenticated release signals with evidence-bound authorization: an APPROVED verdict is a deterministic, auditable function of attested evidence under a pinned policy version. A system-level Release Authorization Soundness theorem formalizes the trust boundaries of this guarantee, explicitly distinguishing between evidence integrity (guaranteed cryptographically) and trace completeness (bounded by the collection boundary). Empirical benchmarks demonstrate a 100.0\% (13/13) block rate across 13 adversarial tamper vectors and a corpus-scale evaluation verifying 1,050 profiles with zero false positives. As autonomous agents assume greater responsibility in production environments, EviAssure provides a concrete architecture for replacing implicit trust in runner logs with cryptographically enforced release authorization.

\section{Ethics and Dual-Use Analysis}\label{sec:appendix_ethics}
The research presented in this paper introduces a defensive mechanism to ensure the security and provenance of autonomous agent releases. This work does not involve human subjects, does not analyze personally identifiable information, and does not conduct active measurements against production systems or networks operated by third parties. The 13 adversarial tamper vectors and the 1,050-profile corpus are fully synthetic and generated within isolated, local test environments for the sole purpose of evaluating the proposed cryptographic and policy enforcement mechanisms. 

\paragraph{Dual-Use Considerations.}
Cryptographic execution attestation mechanisms, if repurposed maliciously, could theoretically be employed to construct invasive employee monitoring frameworks or enforce rigid software lock-in. EviAssure mitigates these dual-use concerns by enforcing decentralized multi-signature threshold governance, open policy schemas (\nolinkurl{governance/release_policy.yaml}), and client-side salted HMAC parameter blinding (\texttt{blind\_payload}). Blinding ensures that operational safety verification remains decoupled from intrusive payload inspection.

\paragraph{Data Privacy \& Parameter Blinding.}
Autonomous software agents frequently process confidential prompt texts, customer financial details, or proprietary source code snippets. To prevent public release audit logs from exposing sensitive data, EviAssure keeps raw payloads out of evidence bundles entirely---traces carry digests only---and the blinding protocol additionally domain-separates those digests with a per-deployment salted HMAC ($H_{\text{blinded}}$), so the same recorded action is not linkable across environments. This preserves full Merkle tree inclusion auditability without storing proprietary inputs in the audit log.

\paragraph{Responsible Disclosure \& Safety Impact.}
By enforcing a strict zero-trust fail-closed release gate, EviAssure provides immediate security benefits for organizations deploying autonomous agents into production. It prevents compromised runner environments or indirect prompt injection vulnerabilities from bypassing deployment safety gates, thereby reducing the systemic risk of unauthorized AI agent deployments in critical infrastructure.
