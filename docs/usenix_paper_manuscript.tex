\title{\Large \bf Evidence-Backed Release Assurance for Autonomous Agent Deployments:\\
Cryptographic Attestation, Fail-Closed Gates, and Tamper-Resilient Audit Infrastructure}

\author{
{\rm Anonymous Submission}

\maketitle

\begin{abstract}
Autonomous agents are promoted to production on the strength of what their execution traces say they did. Every deployed attestation scheme for such traces --- in-toto's runtime-trace predicate, SLSA, TUF, the 2026 agent-provenance drafts, and the per-action receipt schemes that have converged this year --- shares a blind spot: the evidence collector is the sole observer, so an adversary who controls the recording path need not forge anything. It simply does not record. The resulting bundle is internally consistent, every signature verifies, and every integrity check passes, because nothing was tampered with.

This paper makes that gap precise and closes it. We define \emph{Witnessed Trace Completeness}, a property relative to a declared set of witnesses --- the tool endpoints, API gateways and sandbox brokers that actually serve agent actions. Each witness issues receipts carrying a monotonic per-session sequence number and, at session end, a signed commitment to how many actions it served. A release gate then \emph{reconciles} rather than merely verifies. We prove that under EUF-CMA an adversary holding the agent and the collector, but no witness key, cannot omit a witnessed action; and we prove a \emph{separation} result: no scheme whose verdict is a function of a single submitted document can achieve either witnessed completeness or replay-freedom, which places every record-format standard on the wrong side of a formal boundary rather than merely behind on features.

Against \omVectors{} omission attacks, in-toto/DSSE and TUF detect \omDsse{}, per-issuer hash chaining \omChain{}, per-action receipts \omReceipts{}, and \textsc{EviAssure} without reconciliation \omNoWtc{}; with reconciliation it detects \omWtc/\omVectors{}, while an honestly witnessed execution is still approved. On the orthogonal tamper axis it blocks \eviBlocked/\eviTotal{} vectors (\eviPct\%, 95\% CI [\eviCIlo, \eviCIhi]) against \compBlocked{} for an executed in-toto/DSSE + TUF + OPA composition, and we report the one vector it fails. A held-out evaluation over \corpusProfiles{} profiles recalls \insOvertK/\insOvertN{} structurally overt behavioural anomalies and \insStealthK/\insStealthN{} semantically disguised ones, marking where cryptographic release assurance stops and content-level policy must begin.
\end{abstract}

\section{Introduction}
Autonomous software agents driven by Large Language Models (LLMs) operate dynamically across complex tool environments, API endpoints, and persistent memory stores~\cite{jimenez2024swebench, greshake2023not, yao2023react}. Unlike static software artifacts whose behaviors are deterministically governed by compiled code, autonomous agents exhibit non-deterministic reasoning patterns, dynamic tool execution flows, and adaptive multi-step decision sequences. When deploying agent updates, expanding tool privilege scopes, or promoting agentic pipelines to production, organization-wide security depends upon verifying that safety invariants, authorization constraints, and regression test suites have been rigorously validated~\cite{greshake2023not}.

Existing software delivery and release pipelines suffer from a fundamental trust defect: traditional deployment gates evaluate unauthenticated status signals (such as process exit codes, plain text console logs, or un-signed JavaScript Object Notation (JSON) build status files) generated by intermediate runner environments. An attacker who gains control over an intermediate build step, manipulates agent memory traces, or exploits prompt injection vectors can easily forge release approval signals, bypassing security verification entirely~\cite{torres2019in-toto, slsa2023supply, samuel2010surviving, cappos2008look}.

Empirical studies of the open-source ecosystem confirm both the prevalence and the practical exploitability of these compromise paths: taxonomies of documented supply-chain attacks now enumerate hundreds of real incidents~\cite{ladisa2023sok, okafor2022sok}, large-scale measurement work shows package-manager compromise to be routine in interpreted-language ecosystems~\cite{duan2021towards}, and multi-repository update systems require dedicated defenses~\cite{moore2023artemis}.

This leaves an exploitable gap: existing supply chain security focuses almost entirely on attesting the origin and integrity of static software artifacts (e.g., container images, compiled binaries). However, the security posture of an autonomous agent is not defined by its code artifact alone, but by its dynamic, non-deterministic execution traces against a test suite. The fundamental problem is that while we can attest \emph{what} an agent is, current systems cannot cryptographically authorize a release based on \emph{how it behaved}.

To address these critical vulnerabilities, EviAssure\footnote{The complete anonymous source code, evaluation corpus, and benchmark suite are available at \url{https://anonymous.4open.science/r/eviassure-release-assurance/}.} introduces an evidence-backed release assurance architecture that fills this niche. It replaces informal release signals with cryptographically authenticated Evidence Bundles backed by Merkle inclusion proofs, timestamp freshness windows, digital signatures, and provenance envelopes.

\subsection{Key Contributions}
The primary contributions of this work are:
\begin{enumerate}
    \item \textbf{Witnessed Trace Completeness}: a security property, and a protocol achieving it, for the attack class every existing agent-attestation scheme leaves open --- the collector that omits rather than forges. Sequence-bound witness receipts plus a signed closing count make omission require a witness-key forgery. We state the guarantee \emph{relative to a declared witness set} and prove it (Theorem~\ref{thm:wtc}); actions outside that set remain undetectable, and we say so.
    \item \textbf{A separation between record formats and authorization layers}: Theorem~\ref{thm:separation} shows that any scheme whose verdict is a function of one submitted document cannot achieve witnessed completeness or replay-freedom, for information-theoretic rather than engineering reasons. This converts a positioning argument that earlier drafts of this paper made rhetorically into a proof.
    \item \textbf{Evidence-bound release authorization}: a fail-closed gate whose verdict is a deterministic, reproducible function of attested evidence under a pinned policy, with domain-separated (RFC 6962) depth-bound Merkle trace attestation and truncation-resistant count binding.
    \item \textbf{A falsifiable evaluation, including where the system fails}: an omission suite with an honest-execution control, \scoredVectors{} tamper vectors of which five were authored against the design rather than the check list (three broke earlier revisions), executed in-toto/DSSE, TUF, hash-chaining and per-action-receipt baselines, clean negative controls, and a held-out inspection protocol. Every rate carries a Wilson interval, and we report one tamper vector and one detector blind spot that the system does not close.
\end{enumerate}

\paragraph{Record Formats versus Authorization Layers.}
A fundamental distinction separates EviAssure from existing software supply chain metadata standards. Frameworks like in-toto provide signed, tamper-evident attestations of supply-chain steps---including vetted runtime-trace predicates~\cite{intoto_runtime_trace}---and Supply chain Levels for Software Artifacts (SLSA) builds graduated release provenance on top~\cite{torres2019in-toto, slsa2023supply}. However, these frameworks define \emph{passive record formats}. They attest \emph{what occurred} during a static build, but lack a \emph{stateful authorization layer} to actively gate a release based on non-deterministic execution traces. EviAssure is an \emph{active, fail-closed authorization gate}. EviAssure's \texttt{EvidenceBundle} functions as an in-toto v0.2 / SLSA v1.0 compatible envelope, composing directly with existing metadata specifications. EviAssure provides the enforcement mechanisms these specifications omit: (i) truncation-resistant trace binding via a signed trace count, (ii) stateful freshness and replay protection enforced integrally at the gate, and (iii) a mathematically reproducible release decision under a pinned policy. Section~\ref{sec:related-2026} compares EviAssure against recent 2026 AI-agent provenance standards in detail.

\paragraph{Open Science and Reproducibility.}
To support open science and ensure complete reproducibility of our claims, the full source code of EviAssure, the \corpusProfiles{}-profile execution trace corpus, the \scoredVectors{}-vector attack harness with its clean negative controls, and the executed baseline implementations (in-toto/DSSE, TUF, and the Open Policy Agent (OPA) Rego policy) are released as a sanitized, open-source review artifact via an Anonymous GitHub repository (Appendix~\ref{sec:appendix_open_science}).

\section{Preliminaries}\label{sec:preliminaries}
\subsection{Formal Security Definitions}

\begin{definition}[Unforgeability under Chosen Message Attack (EUF-CMA)]
An Evidence Assurance Scheme $\Sigma = (\text{KeyGen}, \text{Package}, \text{Verify})$ is EUF-CMA secure if for all probabilistic polynomial-time adversaries $\mathcal{A}$, the probability that $\mathcal{A}$ outputs a valid pair $(E^*, \sigma^*)$ such that $\text{Verify}(PK, E^*, \sigma^*) = 1$ without $E^*$ having been signed by an honest party holding $SK$ is negligible in security parameter $\lambda$:
\begin{equation}
\text{Pr}[\text{Exp}_{\Sigma, \mathcal{A}}^{\text{euf-cma}}(\lambda) = 1] \le \text{negl}(\lambda)
\end{equation}
\end{definition}

\begin{definition}[Merkle Trace Inclusion Soundness]
For root $R_M$ committed together with its leaf count $N$, and leaf $H_i$, a Merkle proof $\pi_i$ is sound if no computationally bounded adversary can construct $\pi'_i$ for any $H'_i \neq H_i$ --- including internal node digests of the same tree --- such that $\text{VerifyMerkle}(H'_i, \pi'_i, R_M, d) = 1$ for the committed depth $d = \lceil\log_2 N\rceil$, where verification accepts only proof paths of exactly length $d$ and leaves and internal nodes are hashed under disjoint domain prefixes.
\end{definition}

\begin{definition}[Evidence Integrity]\label{def:integrity}
An evidence pack $(R_M, \sigma, N)$ comprising a Merkle root $R_M$, signature $\sigma$, and signed trace count $N$ provides \emph{evidence integrity} if no probabilistic polynomial-time adversary, given oracle access to the honest packager, can produce a verifying pack $(R'_M, \sigma', N')$ that the packager never issued; equivalently, nothing that was \emph{recorded} can be modified, reordered, inserted, or removed without detection. Integrity is a property of the signed record and is guaranteed by Theorem~\ref{thm:failclosed} below.
\end{definition}

\begin{definition}[Trace Completeness]\label{def:completeness}
Let $E$ be an agent execution and let $\mathcal{C}$ be the evidence collector that observes $E$. A recorded trace set $T = \{T_1, \dots, T_N\}$ is \emph{complete with respect to $E$} if every action of $E$ that $\mathcal{C}$ observed is represented by exactly one $T_i$. Completeness is an observation property of the \emph{collector}, not of the Merkle tree: the tree attests exactly the leaves it was given. If a real execution is $A \rightarrow B \rightarrow C \rightarrow D \rightarrow E$ but the recorded trace is $A \rightarrow B \rightarrow D \rightarrow E$, the tree protects the recorded sequence perfectly and says nothing about $C$. No signature, hash chain, or inclusion proof over the submitted set can, because the adversary forged nothing --- it declined to create evidence. Definition~\ref{def:wtc} makes this attainable by moving the observation out of the collector's trust domain.
\end{definition}

\begin{definition}[Witnessed Trace Completeness]\label{def:wtc}
Let $\mathcal{W}=\{W_1,\dots,W_m\}$ be a set of \emph{witnesses}, each holding a signing key the adversary does not control, and let $\mathsf{med}(W_j)$ be the set of action types $W_j$ mediates. An action is \emph{witnessed} if its type lies in $\bigcup_j \mathsf{med}(W_j)$. A submitted trace set $T$ for session $\mathit{sid}$ is \emph{witness-complete} if for every $W_j \in \mathcal{W}$ there is a $W_j$-signed closing $(\mathit{sid}, n_j)$, the $W_j$-signed receipts in $T$ are exactly the contiguous sequence $1,\dots,n_j$ for $\mathit{sid}$, each receipt binds to a distinct member of $T$, and every witnessed action in $T$ carries a receipt.

Completeness is stated \emph{relative to} $\mathcal{W}$: an action of a type no witness mediates is outside the guarantee. This is a deployment-controllable condition --- mediate every externally observable effect --- rather than the unbounded assumption that the collector observed everything.
\end{definition}

\begin{theorem}[Witnessed Completeness Soundness]\label{thm:wtc}
Let $\mathcal{A}$ control the agent, the evidence collector and the collector's signing key, but no key in $\mathcal{W}$. If the gate accepts a witness-complete bundle for session $\mathit{sid}$, then except with probability $m \cdot \mathrm{Adv}^{euf\text{-}cma}_{\mathrm{Ed25519}}$, the trace set contains every witnessed action performed in $\mathit{sid}$.
\end{theorem}

\begin{proof}
Suppose $\mathcal{A}$ omits a witnessed action $a$ served by $W_j$ as its $k$-th action, and the gate accepts. $W_j$'s counter is monotone and advances only on service, so $W_j$ issued receipts $1,\dots,n_j$ with $k \le n_j$, and its closing commits to $n_j$. Acceptance requires the receipt sequence for $W_j$ to be exactly $1,\dots,n'_j$ with a matching closing. Three cases. (i) $n'_j = n_j$: then $\mathcal{A}$ supplied $n_j$ distinct receipts, but only $n_j - 1$ correspond to submitted actions, so some receipt is unmatched and reconciliation rejects --- unless $\mathcal{A}$ minted a receipt, an Ed25519 forgery under $W_j$. (ii) $n'_j < n_j$: the presented closing differs from the one $W_j$ signed, so $\mathcal{A}$ forged a closing under $W_j$. (iii) $\mathcal{A}$ substitutes a receipt from another session $\mathit{sid}' \neq \mathit{sid}$: the session identifier is inside the signed receipt payload, so the substitution is rejected without forgery. Each surviving case is a forgery against one of $m$ witness keys; a union bound gives the stated advantage. Fabrication of a witnessed action is symmetric: the action carries no receipt, and minting one is again a forgery. $\square$
\end{proof}

\begin{theorem}[Record Formats Cannot Achieve These Properties]\label{thm:separation}
Let $V$ be a \emph{stateless document verifier}: a deterministic predicate $V(d) \in \{\mathrm{accept},\mathrm{reject}\}$ over a single submitted document $d$, with access to fixed public parameters (trust roots, policy) but no state that varies with prior submissions and no channel to $\mathcal{W}$. Then $V$ achieves neither replay-freedom nor witnessed completeness.
\end{theorem}

\begin{proof}
\emph{Replay-freedom.} Determinism gives $V(d)=V(d)$: if $V$ accepts $d$ once it accepts every resubmission, so an adversary replays an approved release indefinitely. Distinguishing first from subsequent submission requires state that varies across submissions, which $V$ by definition lacks.

\emph{Witnessed completeness.} Fix a witness $W$ and consider two executions: $E_1$ serving $n$ actions, and $E_2$ serving the same first $n-1$ and then a further action whose record the adversary omits. Let $d_1, d_2$ be the honestly-signed documents. Every attestation in $d_2$ is genuine: the collector signs truthfully over what it recorded, and each retained receipt is authentic. So $d_1$ and $d_2$ are identically distributed over every field $V$ can inspect, and $V(d_1)=V(d_2)$. Since $V$ must accept $d_1$ (a correct execution), it accepts $d_2$. The only field that could differ is a commitment to $W$'s served count, which $W$ alone can produce --- and requiring it makes the verifier's input depend on a trust domain outside $d$, contradicting statelessness.
\end{proof}

Theorem~\ref{thm:separation} is why we describe in-toto, SLSA, TUF, AAS-1 and \texttt{agent-decision} as record formats rather than as weaker gates. Their verification is by construction a function of the submitted document; the gap is structural, not a matter of maturity, and Section~\ref{sec:omission} measures it.

\section{System Architecture and Threat Model}\label{sec:system_threat}

\textbf{Intuition.} EviAssure turns an agent's step-by-step execution path into a signed, Merkle-committed evidence bundle before deployment, and evaluates that bundle at a \emph{fail-closed gate} that denies release whenever a required proof, signature, or threshold is missing, malformed, or compromised.

\subsection{System Model}
The EviAssure release assurance architecture involves four primary entities: the \emph{Evidence Collector}, the \emph{Key Management System (KMS)}, the \emph{Policy Registry}, and the \emph{Release Assurance Gate} (Figure~\ref{fig:architecture}).

\textbf{Evidence Collector}: in production, an out-of-process monitor outside the agent's sandbox, observing activity via eBPF syscall tracepoints and container network proxies. \emph{In this evaluation it is Python instrumentation wrappers} --- the paper's principal validity threat (Section~\ref{sec:limitations}).
\textbf{Cloud KMS / HSM}: signing authority is rooted outside the runner; the collector obtains signatures over canonical digests without holding key material. The gate checks the declared ARN against \texttt{kms\_key\_arn\_pattern}, a misconfiguration control rather than an adversarial one (Section~\ref{sec:limitations}).
\textbf{Policy Registry}: an out-of-band store for release policies, pinned public keys, and the revocation list.
\textbf{Release Assurance Gate}: the enforcement entity, running in a trusted CI/CD step, evaluating the signed \texttt{EvidenceBundle} against the pinned policy.

\subsection{Adversary Model}\label{sec:threat}
The security model considers a powerful adversary $\mathcal{A}$ attempting to deploy an unapproved, regression-prone, or malicious agent update to production environments~\cite{shostack2014threat, carlini2024poisoning, schuster2021get}. The adversary $\mathcal{A}$ may control intermediate runner environments, network transit layers, or build scripts. 

\paragraph{Trust Model Boundaries.} EviAssure assumes that the underlying cryptographic primitives (Ed25519 and SHA-256) remain computationally intractable for PPT adversaries, and that the Cloud KMS / HSM service faithfully enforces identity access control over private signing keys. In addition, the system requires strict environment isolation: if an autonomous agent escapes its sandboxed execution tier to gain local file access or arbitrary code execution over the assurance engine or the collector host process, it can forge an evidence payload \emph{prior} to KMS signing. Such a compromise of the assurance engine's trusted computing base is an explicit out-of-scope limitation, meaning the cryptographic guarantees hold assuming a tamper-proof assurance control plane. Physical hardware side-channel attacks on HSM microchips, total subversion of the cloud provider's root KMS master keys, and hypervisor rootkits are likewise out-of-scope for the release gate layer.

We categorize $\mathcal{A}$'s in-scope capabilities into five adversary capability classes,, mapped to vectors in Table~\ref{tab:tamper}. These cover runner and memory tampering ($\mathcal{A}_1$), network and signature forgery ($\mathcal{A}_2$), replay and time skew ($\mathcal{A}_3$), governance bypass ($\mathcal{A}_4$), and serialization malleability ($\mathcal{A}_5$).
\subsection{Security Requirements}
The EviAssure construction is proved against the following fundamental security requirements, subject to the defined trust boundaries:

\begin{enumerate}
    \item \textbf{Evidence Integrity}: The gate must ensure that no recorded action can be modified, reordered, inserted, or removed without detection (Definition~\ref{def:integrity}).
    \item \textbf{Trace Completeness}: While integrity is cryptographic, the system requires the collection boundary to capture all actions honestly. The gate must bind the attestation specifically to the count of recorded actions to prevent silent truncation (Definition~\ref{def:completeness}).
    \item \textbf{Release Authorization Soundness}: The release decision must be a deterministic function of the signed evidence and the pinned policy. No PPT adversary should induce an APPROVED verdict for modified or malicious traces.
    \item \textbf{Trace Privacy (Parameter Blinding)}: Sensitive trace parameters and intermediate data should remain completely hidden from public verifiers or auditors via indistinguishable salted HMAC blinding.
\end{enumerate}

The release gate enforces a strict zero-trust fail-closed guarantee against these requirements: any evidence payload failing verification is rejected with exit code 1 (\texttt{BLOCKED}). As discussed under trace completeness, EviAssure scopes its guarantees to the \emph{collection boundary}---the same boundary every attested-execution system faces~\cite{apas2026agent-provenance, aas12026agent-audit}. Residual risk is mitigated by collecting evidence at the outermost observable boundary and by semantic inspection.

\section{Cryptographic Evidence Attestation}
EviAssure establishes verifiable release claims by packaging agent action histories into cryptographically attested evidence bundles. This section describes the Merkle tree aggregation protocol, browser Document Object Model (DOM) attestation, trace parameter blinding, and SLSA v1.0 / in-toto predicate envelopes.

\subsection{Execution Trace \& Browser UI Attestation Schema}
Each execution trace record $T_i$ captures structured action metadata across autonomous agent steps. For API and backend tool calls, $T_i$ records:
\begin{equation}
T_i = (\text{id}_i, \text{agent}_i, \text{action}_i, \text{status}_i, \text{duration}_i, H_{\text{out},i})
\end{equation}
For browser and UI agent steps, EviAssure extends attestation to capture DOM state hashes ($H_{\text{DOM}}$) and visual screenshot render digests ($H_{\text{screen}}$):
\begin{equation}
\resizebox{\columnwidth}{!}{$
T_{\text{UI},i} = (\text{id}_i, \text{agent}_i, \text{action}_i, \text{url}_i, \text{elem}_i, H_{\text{DOM},i}, H_{\text{screen},i})
$}
\end{equation}
$H_{\text{DOM}}$ is computed over the serialized DOM state of the rendered page, $H_{\text{DOM},i} = \text{SHA256}(\text{DOM}_{\text{serialized}})$: the specimen serializes the rendered document deterministically before hashing, so identical page states yield identical digests while any mutation (e.g., an injected modal dialog or altered form control) changes the digest. Visual render digests $H_{\text{screen},i} = \text{SHA256}(\text{render})$ capture rendered canvas pixels under deterministic software rasterization (e.g., headless Chromium with \texttt{--disable-gpu}, \texttt{--font-render-hinting=none}, and pinned viewport dimensions on an immutable container base image to eliminate cross-driver subpixel anti-aliasing drift). Each trace record produces a canonical leaf digest $H_i = \text{SHA256}(T_i.\texttt{to\_hash}())$. The canonical leaf serialization commits \emph{every} schema field---identifier, agent, action, status, duration, and output digest---so modifying any recorded field after signing, including the timing \texttt{duration\_ms}, invalidates the recomputed root and is rejected by the gate.

\subsection{Witness Protocol}\label{sec:witness}
A witness is the component that \emph{actually serves} an agent action: a tool endpoint, an API gateway, a database proxy, a sandbox syscall broker. It is not part of the agent runtime, and the entire security argument rests on one property --- the adversary who owns the agent and the collector does not hold witness keys.

Each witness keeps a monotonic counter per session. On serving action $a$ in session $\mathit{sid}$ it returns
\begin{equation}
r = \mathrm{Sign}_{W_j}(\mathit{sid},\ \mathrm{seq},\ H_{\mathrm{act}}(a))
\end{equation}
where $H_{\mathrm{act}}$ digests the action identity the witness can see (requester, operation, returned digest) rather than the full Merkle leaf, whose timing fields are collector-side. At session end $W_j$ emits $\mathrm{Sign}_{W_j}(\mathit{sid}, n_j)$, committing to how many actions it served. \textbf{Every registered witness closes every session}, including with $n_j=0$: without that rule, dropping a witness's actions \emph{and} its closing is indistinguishable from never using the tool, which is vector O3.

The gate reconciles: authenticate every attestation under a registry-pinned witness key; require the session identifier to match; require each witness's receipts to form exactly $1..n_j$; require every receipt to bind to a submitted trace; and require every trace claiming a mediated action to carry a receipt. The bundle signature covers a digest of the whole attestation set, so a collector cannot delete receipts from a signed bundle and leave the signature intact.

\paragraph{Cost and deployment.} A receipt is one Ed25519 signature over 100 bytes at the point of service, and the gate performs $O(|T|)$ verifications. The real cost is organisational, not computational: witnesses must be deployed at the boundaries that matter, and Definition~\ref{def:wtc} makes the resulting guarantee exactly as strong as that deployment. We regard stating the guarantee relative to a declared, auditable witness set as an improvement over assuming a perfect collector, not as a weaker claim.

\paragraph{Parameter blinding.} Bundles carry digests, never raw payloads. A keyed HMAC mode (\texttt{blind\_payload}) additionally re-keys those digests per deployment, which buys unlinkability across environments and resistance to dictionary recovery of low-entropy outputs --- $\mathrm{SHA256}(\texttt{"TOKEN\_VALIDATED"})$ is recoverable by exhaustive search, the salted HMAC is not. It is deterministic, so it does not conceal repetition within one deployment. We record it as a hardening measure rather than a contribution.

\subsection{Merkle Trace Aggregation and Sparse Proof Compression}
To attest $N$ execution traces without transmitting full raw logs to every gate request, EviAssure aggregates normalized trace digests into a SHA-256 Merkle tree~\cite{merkle1989digital, laurie2014certificate}. Each trace record $T_i$ maps to leaf digest $H_i$.

For $N=1,000$ traces, transmitting raw trace logs requires 222.6 KB of storage, scaling to 220,705.03 KB for $N=1,000,000$ traces. EviAssure provides sparse Merkle proof compression, transmitting the 32-byte root $R_M$ and $O(\log N)$ inclusion proof paths $\pi_i$ for audited steps. 

Given proof path $\pi_i = \{(P_1, \text{pos}_1), \dots, (P_K, \text{pos}_K)\}$, inclusion is verified recursively by setting $C_0 = H_i$ (the committed leaf digest; leaf digests are already SHA-256 strings and are \emph{not} re-hashed at the proof boundary, matching \texttt{verify\_merkle\_proof}) and evaluating:
\begin{equation}
C_j = \begin{cases}
\text{SHA256}(C_{j-1} \parallel \text{``:''} \parallel P_j), & \text{if } \text{pos}_j = \text{right} \\
\text{SHA256}(P_j \parallel \text{``:''} \parallel C_{j-1}), & \text{if } \text{pos}_j = \text{left}
\end{cases}
\end{equation}
Leaves and internal nodes are hashed under \emph{disjoint domain prefixes} following RFC 6962~\cite{laurie2014certificate}: a leaf commits $\text{SHA256}(\texttt{0x00} \parallel T_i.\texttt{to\_hash}())$ and an internal node commits $\text{SHA256}(\texttt{0x01} \parallel L \parallel R)$ over the raw 32-byte child digests. An earlier revision of this system instead hashed both as unprefixed SHA-256 over an ASCII string with a \texttt{:} delimiter and argued that the fixed 129-byte node preimage supplied domain separation. It does not: the two input languages merely failed to overlap for the leaf schema in use, which is an accident of the schema rather than a property of the construction. Explicit prefixes make the separation structural.

The proof is valid if and only if $C_K = R_M$ \emph{and} the path length equals the committed tree depth $d=\lceil\log_2 N\rceil$ derived from the signed execution trace count. The two defences are independent and both are necessary: domain separation prevents an internal digest from ever being interpreted as a leaf, and the depth bound prevents the shortened-path substitution of the CVE-2012-2459 family, which succeeds without any hash collision. Vector V15 (Section~\ref{sec:tamper}) exercises exactly this attack against the third-party auditor path; earlier revisions of this system failed it. Transmission size for an audited step remains $<5\text{ KB}$.

\begin{lstlisting}[language=python,caption={Merkle Trace Aggregation Protocol.},label={lst:proto1}]
LEAF, NODE = b"\\x00", b"\\x01"   # RFC 6962 domain separation

def leaf_digest(content):
    return sha256(LEAF + content.encode()).hexdigest()

def node_digest(l, r):
    return sha256(NODE + bytes.fromhex(l)
                       + bytes.fromhex(r)).hexdigest()

def build_merkle_tree(leaf_digests):
    current, levels = leaf_digests, [leaf_digests]
    while len(current) > 1:
        current = [node_digest(current[i],
                     current[i+1] if i+1 < len(current)
                                  else current[i])
                   for i in range(0, len(current), 2)]
        levels.append(current)
    return current[0], levels
\end{lstlisting}

Listing~\ref{lst:proto1} implements the recursive aggregation of agent trace hashes into the final $O(\log N)$ verifiable structure.

\section{Fail-Closed Policy Verification Engine}
Release authorization in EviAssure is governed by a zero-trust policy engine (\textnormal{\texttt{ReleasePolicyEngine}}) that enforces mandatory fail-closed default rules. This section details the declarative policy schema, multi-factor evaluation protocol, key governance rules, and the system-level formal security analysis.

\subsection{Declarative Policy Governance Rules}
A release policy specification $P$ defines strict quantitative safety thresholds and cryptographic verification conditions:
\begin{equation}
\begin{split}
P = (\,P_{\text{min\_pass}},\ &P_{\text{max\_drift}}, P_{\text{min\_sigs}}, P_{\text{valid\_window}},\\
&\mathcal{K}_{\text{trusted}}, \mathcal{K}_{\text{rev}}, \mathcal{A}_{\text{KMS}})
\end{split}
\end{equation}
where:
\begin{itemize}
    \item $P_{\text{min\_pass}}$: Minimum required unit and integration test pass rate (default: $100.0\%$ (100/100)).
    \item $P_{\text{max\_drift}}$: Maximum allowable unresolved security drift findings (default: $0$).
    \item $P_{\text{min\_sigs}}$: Required threshold number of valid signatures from authorized keys (default: $K=1$).
    \item $P_{\text{valid\_window}}$: Evidence timestamp freshness validity window $\Delta T_{\text{max}} = 3,600\text{ s}$ ($1\text{ hour}$) with a maximum future clock skew tolerance of $\delta_{\text{skew}} = 30\text{ s}$ (assuming RFC 5905 NTP synchronization across runner nodes).
    \item $\mathcal{K}_{\text{trusted}}$: Trusted key registry pinning authorized signing key IDs to their Ed25519 public keys (\nolinkurl{governance/trusted_keys.yaml}). Signature verification uses the pinned key, never a public key supplied inside a submitted bundle; unregistered key IDs are rejected. The registry follows the key-accountability patterns of key transparency~\cite{melara2015coniks} and delegation hierarchies~\cite{kuppusamy2016tuf}: verification authority rests on a small, versioned, offline-pinnable root set rather than on keys that travel with the evidence.
    \item $\mathcal{K}_{\text{rev}}$: Key Revocation List (CRL) tracking compromised or deprecated key identifiers.
    \item $\mathcal{A}_{\text{KMS}}$: Required Cloud KMS or HSM key ARN boundary pattern matching.
\end{itemize}

Listing~\ref{lst:proto2} outlines the complete zero-trust verification algorithm enforced by \textnormal{\texttt{ReleasePolicyEngine}}.

\begin{lstlisting}[language=python,caption={Fail-Closed Policy Gate Verification Protocol.},label={lst:proto2}]
# In: Evidence E, Policy P, revoked K_rev, seen N_seen
# Out: D in {APPROVED, BLOCKED}; any exception => BLOCKED
def evaluate_release_gate(E, P, K_rev, N_seen):
    if N_seen is None: return BLOCKED  # no replay state
    valid = set()
    for s in E.signatures:
        if s.key_id in K_rev: continue
        if s.key_id not in K_trusted: continue   # registry
        pk = K_trusted[s.key_id]                 # pinned only:
        if s.pub_key and s.pub_key != pk: continue
        if not match_kms_arn(s.kms_arn, P.kms): continue
        if verify_ed25519(canon(E), s.sig, pk):
            valid.add(s.key_id)          # distinct signers
    if len(valid) < P.min_signatures:     return BLOCKED
    if merkle_root(E.traces) != E.merkle_root: return BLOCKED
    if E.traces_count != len(E.traces):   return BLOCKED
    if E.test_pass_pct < P.min_pass_pct:  return BLOCKED
    if E.unresolved_drift > P.max_drift:  return BLOCKED
    if E.nonce in N_seen:                 return BLOCKED
    if not fresh(E.timestamp, P.window, skew=30): return BLOCKED
    N_seen.add(E.nonce);  return APPROVED
\end{lstlisting}

Listing~\ref{lst:proto2} outlines the zero-trust policy engine logic that strictly enforces fail-closed behavior on signature or trace discrepancies.

\subsection{Formal Security Analysis}\label{sec:proofs}

The security analysis proceeds in two layers. Theorem~\ref{thm:failclosed} is the primitive-level argument: a sequence of games showing what no adversary can do to the cryptographic components, reducing to EUF-CMA and collision resistance. Theorem~\ref{thm:authorization} is the system-level argument: it states what an APPROVED verdict \emph{means} --- the actual security objective of a release gate --- and makes explicit the trust boundaries (evidence collector, key registry, nonce state) on which that meaning rests.

\begin{theorem}[Fail-Closed Release Soundness]\label{thm:failclosed}

Under the assumption that Ed25519~\cite{bernstein2012high} is EUF-CMA secure~\cite{goldwasser1988digital, brendel2021ed25519} and SHA-256 is collision-resistant, no probabilistic polynomial-time adversary $\mathcal{A}$ can induce \textnormal{\texttt{ReleasePolicyEngine}} to output $\text{APPROVED}$ for a modified trace history, forged signature, replayed nonce, or non-compliant evidence payload except with negligible probability $\text{negl}(\lambda)$.
\end{theorem}

\begin{proof}
Two game hops carry content; the remainder of the gate is deterministic.
$\mathbf{Game}_1$ aborts if $\mathcal{A}$ produces a valid signature over a payload the honest packager never issued. \emph{Reduction:} an EUF-CMA adversary $\mathcal{B}$ installs its challenge key as the sole registry entry, answers packaging requests via its signing oracle on $\mathrm{canon}(E)$, and computes every other check itself, so the simulation is perfect; a $\text{Game}_1$ abort yields a forgery on $\mathrm{canon}(E^*)$, which by injectivity of the canonical encoding was never queried. $\mathbf{Game}_2$ aborts if $\mathcal{A}$ finds $\mathcal{T}^* \neq \mathcal{T}$ with $\mathrm{MerkleRoot}(\mathcal{T}^*)=R_M$; with domain-separated leaves and the committed depth, substitution requires a SHA-256 collision. Replay, freshness, revocation, registry membership and threshold comparison are table lookups over the signed payload: they reject with probability $1$ given correct gate state and contribute no term. Hence
\begin{equation}
\mathrm{Adv}^{\text{tamper}}_{\textsc{EviAssure}} \le \mathrm{Adv}^{euf\text{-}cma}_{\mathrm{Ed25519}}(\mathcal{B},t,q_s) + \mathrm{Adv}^{coll}_{\mathrm{SHA256}}(\mathcal{C},t)
\end{equation}
Both terms are concrete: Ed25519 and SHA-256 are fixed-parameter primitives, so we read the bound at the 128-bit level rather than asymptotically in $\lambda$.
\end{proof}

Theorem~\ref{thm:failclosed} bounds an adversary's ability to \emph{fake} evidence; it says nothing on its own about what a genuine, honestly-signed evidence pack entitles its holder to. That is the release-gate question, and it is Theorem~\ref{thm:authorization}.

\begin{theorem}[Evidence-Bound Release Authorization Soundness]\label{thm:authorization}
Fix a policy version $P$ and a trusted key registry $\mathcal{K}_{\text{trusted}}$. If \textnormal{\texttt{ReleasePolicyEngine}} outputs $\text{APPROVED}$ for evidence $E$, then, except with probability $\text{negl}(\lambda)$, all of the following hold:
\begin{enumerate}
    \item[(i)] \textbf{Authenticity:} $E$ carries a valid Ed25519 signature by a non-revoked key pinned in $\mathcal{K}_{\text{trusted}}$; attacker-generated keys, spoofed key IDs, and revoked keys cannot produce a valid signature.
    \item[(ii)] \textbf{Evidence binding:} the recomputed Merkle root over the submitted trace set equals the signed root, the signed trace count equals the number of submitted traces, and every inclusion proof binds to the committed tree depth under disjoint leaf/node domains. The trace set the gate evaluated is therefore \emph{the one the collector signed} --- no trace was added, removed, reordered or edited between collection and adjudication. This says nothing about the relation between the signed trace set and the underlying execution; that gap is Definition~\ref{def:completeness} and is not closed by any cryptographic check.
    \item[(iii)] \textbf{Freshness:} the timestamp lies within the validity window $\Delta T_{\text{max}}$ and the skew bound $\delta_{\text{skew}}$, and the nonce has not been processed within the window; the release is not a replay of an earlier approved bundle.
    \item[(iv)] \textbf{Policy compliance:} all declared thresholds (test pass rate, unresolved drift, KMS ARN boundary, signature threshold $K$) satisfy policy version $P$; an APPROVED verdict under a different policy version is not an APPROVED verdict for this release.
\end{enumerate}
\end{theorem}

\paragraph{Scope and Operational Assumptions.}
The guarantees hold conditionally on (a) the \emph{collector assumption} of Definition~\ref{def:completeness} --- the evidence collector observed and recorded every action of the release execution --- which supplies the completeness half of the guarantee, and (b) the \emph{key-management assumption} --- registry keys are honestly generated and the HSM/KMS enforces the ARN boundary. The theorem asserts nothing about actions that never reached the collector, nor about the semantic correctness of recorded trace content; both are defined in the threat model and handled by the out-of-band semantic inspection layer.

\begin{proof}
\textbf{(i)} Follows from Theorem~\ref{thm:failclosed}, Game$_1$, plus the deterministic registry checks enforced before any signature verification (\texttt{policy.py}): unknown key IDs, bundle-supplied keys disagreeing with the registry, and revoked keys are rejected outright, so per-signature success is bounded by $\text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A})$. \textbf{(ii)} Follows from Theorem~\ref{thm:failclosed}, Game$_2$, plus the deterministic signed-count check $N = |\text{traces}|$; substitution requires either a hash collision or a broken signature. \textbf{(iii)} Freshness, skew, and nonce checks are deterministic (Game$_3$; Listing~\ref{lst:proto2}) and hold with probability $1$ given correct gate state, with the disclosed caveat that replay protection requires sharing the nonce cache across gate replicas in distributed environments. \textbf{(iv)} Threshold comparisons are deterministic over the signed payload and the pinned policy version. Composition yields the statement; the only probabilistic terms reduce to the primitive advantages of Theorem~\ref{thm:failclosed}.
\end{proof}

EviAssure was deployed as a production GitHub Action (\nolinkurl{.github/actions/evidence-release-gate/action.yml}) and an in-toto v0.2 layout specification (\nolinkurl{governance/intoto_layout.json}). Evaluation tested two primary agentic workflow specimens:
\begin{enumerate}
    \item \textbf{Backend Multi-Step Workflow Specimen} (\nolinkurl{specimens/agent_runner.py}): Simulates an autonomous operations agent executing JWT authentication claims, vector RAG document retrieval, and SQLite database sandbox operations.
    \item \textbf{Browser UI Action Specimen} (\nolinkurl{specimens/web_app_runner.py}): Simulates a web-browser autonomous agent executing page navigation, button clicks, DOM state hashing ($\text{SHA256}(\text{DOM}_{\text{serialized}})$), and screenshot render-reference digests ($\text{SHA256}(\text{render})$).

\subsection{CI/CD Integration}
The gate ships as a GitHub Action that loads the pinned key and witness registries and the policy, ingests the \texttt{EvidenceBundle}, runs \texttt{ReleasePolicyEngine} (\nolinkurl{scripts/verify_release_gate.py}), and on failure emits structured diagnostics and exits non-zero on every output path.

\subsection{Agent Execution Trace Corpus (\texorpdfstring{$N=\corpusProfiles$}{N=1,075})}\label{sec:corpus}
The corpus (\nolinkurl{corpus/agent_trace_corpus.json}) contains \corpusProfiles{} profiles / \corpusRecords{} trace records across five agent architectures, each profile carrying four to six steps: \corpusClean{} clean, \corpusOvert{} \emph{overt} anomalies over ten classes, and \corpusStealth{} \emph{stealth} anomalies over five classes. It is entirely synthetic and templated; this is stated in the artifact's own \texttt{provenance} field and is the principal threat to external validity (Section~\ref{sec:limitations}).

The overt/stealth split exists because an earlier revision of this corpus was not a benchmark. Every planted anomaly used an action name and a status string that appeared nowhere in clean traffic, and the inspection layer keyed off a hard-coded list of exactly those action names --- the generator and the detector were the same list, written together. The reported 50/50 recall was a property of the generator. \emph{Overt} classes retain that structure (out-of-vocabulary action and status) and are the easy half. \emph{Stealth} classes are the point: a mutating statement issued through the read-only query path, a ledger transfer to an attacker-controlled destination, retrieval returning injected context, extraction used as an exfiltration channel, a linter invoked with findings suppressed. Each uses an action, a status and a duration drawn from clean traffic, so no per-leaf vocabulary or envelope test can separate them. Section~\ref{sec:twolayer} reports both halves separately.
\subsection{Forensics and Diagnostics: CLI Inspection \& Audit Tool}\label{sec:forensics}
To assist security incident response teams during post-incident investigations, EviAssure provides an offline forensic inspection utility (\nolinkurl{scripts/audit_trace_forensics.py}). The forensic tool parses serialized \texttt{EvidenceBundle} files, reconstructs the full Merkle tree, verifies Ed25519 public key signatures against trusted CRL stores, and isolates specific leaf index anomalies. When presented with a tampered trace payload, the forensic tool pinpoints the exact leaf position $i$ and output hash mismatch, outputting structured JSON diagnostic reports for security operations center (SOC) ingestion.

\section{Systems Security Evaluation}\label{sec:eval}
The empirical evaluation validates EviAssure across a deliberate two-part strategy: a micro-level validation of the gate's enforcement mechanisms, and a macro-level evaluation of the overall system deployed at scale. 

\textbf{Mechanism Evaluation.} The gate's baseline performance is evaluated through Merkle tree scaling latency and multi-core verifier throughput. Adversarial tamper resilience is measured against a suite of 13 targeted attack vectors. Twelve vectors are derived from the five adversary capability classes ($\mathcal{A}_1$--$\mathcal{A}_5$) and exercise one enforcement each; five further vectors were authored against the design rather than the check list, and are the ones with the power to fail. Clean negative controls measure the false-block rate, without which a block rate is uninterpretable.

\textbf{System-Level Deployment.} To evaluate the gate on realistic workloads, we conduct a corpus-scale evaluation over \corpusProfiles{} agent trace profiles, demonstrating the interaction between the cryptographic integrity gate and an out-of-band semantic inspection layer --- and, importantly, where that interaction leaves a gap.

Results are split by kind. \emph{Deterministic} security results (block counts, ablation, inspection) are produced by \nolinkurl{scripts/run_security_eval.py} into \nolinkurl{results/security_evaluation.json} and are platform-independent: they reproduce identically on any machine. \emph{Timed} measurements are wall-clock timings recorded by \nolinkurl{scripts/run_release_benchmark.py} into \nolinkurl{results/benchmark_summary.json} on an Apple M4 Max with 14 cores (10 performance, 4 efficiency; no SMT, so logical and physical core counts coincide) running Python 3.14.x. Each scaling point, throughput configuration, proof cost, blinding cost, and hashing figure is the mean over \benchRepeats{} runs, with the standard deviation recorded alongside in the artifact (\texttt{*\_std} fields); per-worker throughput aggregates 1,000 policy evaluations per run. Tamper vectors and gate verdicts are deterministic checks evaluated once each, so run-to-run dispersion there is zero by construction; sampling uncertainty over the finite vector set is reported instead, as a Wilson 95\% interval on every rate.

\subsection{Multi-Core Parallel Verifier Throughput}
Verifier throughput was evaluated using a Python \texttt{ProcessPoolExecutor} across 1, 2, 4, 8, and 16 worker cores over 1,000 evaluation requests per run and \benchRepeats{} runs per configuration; each evaluation is a distinct fresh-nonce bundle against a warm policy engine (evidence creation and replay-state checks are measured separately, so the timed region is steady-state verification). \textbf{The mechanism vectors do not demonstrate resilience.} V1--V12 map close to one-to-one onto the gate's checks, because we wrote both; they are a completeness test for the implementation and nothing more. An earlier version of this paper argued that a 1:1 map ``proves the engine covers the complete formal domain without coverage gaps''. That argument is invalid, and V14 and V17 are why.

\textbf{Three vectors ($\dagger$) broke earlier revisions.} V14 exploits a disabled trusted-key registry: the gate then verified against the public key carried \emph{inside the submitted bundle}, so an adversary with their own keypair and a conformant KMS ARN string was APPROVED with zero violations. The shipped verifier persists nonces and fails closed when the ledger is unavailable, but cross-replica correctness needs shared storage the prototype does not provide.

\textbf{Differential wire fuzzing.} We replaced the previous mutation campaign, which reported 1,000/1,000 blocked. That result carried no information: every mutation class perturbed a field inside the Ed25519-signed payload, so a verifying bundle was unreachable by construction, and the campaign contained no clean cases so it could not detect false blocks either. The replacement perturbs the \emph{serialization} of a validly signed bundle --- key order, insignificant whitespace, unicode escaping, number formatting, duplicate keys, byte-order marks --- where both outcomes are reachable. Over \fuzzCases{} cases (20\% clean controls): \fuzzBlockedK/\fuzzBlockedN{} semantics-changing encodings blocked, \fuzzApprovedK/\fuzzApprovedN{} semantics-preserving encodings approved. This campaign found a real defect: the duplicate-key detector accumulated key counts across every object in the document, so sibling objects in the \texttt{traces} array registered as duplicates and any deployment actually supplying the raw wire text rejected every multi-trace bundle. It is fixed and regression-tested.

\subsection{Per-Check Ablation}
Each enforcement was disabled in turn and the suite re-evaluated (matrix in the artifact's \texttt{ablation} block). Disabling the signature check releases V1, V3, V9, V14 and V18; removing Merkle re-derivation releases V2 and V8; the quality, drift, freshness and replay checks each release exactly the vectors they target (V7; V6; V5 and V11; V4). V16 escapes every variant, including the full gate.

Two results are worth stating precisely, because the previous version of this section stated one of them incorrectly.

First, \textbf{not every check is necessary against this suite}. Disabling the signed trace-count binding releases no vector: V12 is independently caught by root recomputation. The count binding earns its place by protecting the \emph{auditor} path --- proof depth is derived from the signed count --- not by adding coverage at the gate. We previously wrote that ``every check is necessary''; the artifact's own matrix contradicted it.

Second, \textbf{emptying the trusted-key registry collapses the gate rather than weakening it}: all Ed25519 evidence is rejected because no signature can be authenticated. This is now true of the implementation. It was not true when we first claimed it: the ablation variant set a \texttt{require\_trusted\_key} flag which, far from disabling verification, redirected it to the bundle-supplied key --- the V14 bypass. The registry is the trust anchor, but establishing that required fixing the code, not re-reading the matrix.

\subsection{Omission Attacks}\label{sec:omission}
The tamper suite and the omission suite test different things. A tamper vector modifies evidence and is caught by an integrity check. An omission vector modifies \emph{nothing}: the adversary performs an action and declines to record it, then signs honestly over what remains. There is no discrepancy to detect, which is why Theorem~\ref{thm:separation} rules the class out for document verifiers rather than merely predicting they will do badly at it.

This is the precise limitation of AAS-1's omission story, and it is why the closing count, not the chain, is what makes truncation detectable.

\subsection{Comparative Gate Analysis}\label{sec:comparative}
The previous version of this comparison was not defensible and we have rebuilt it. It scored a ``Sigstore/Cosign-style'' gate implemented as \texttt{signed and signature is not None} --- a presence check on a JSON field --- and an ``exit-code gate'' implemented as \texttt{test\_pass\_pct > 0}. Against a vector set derived from our own check list, both scored near zero by arithmetic, and the resulting figures appeared in the abstract as though they characterised the state of the art. They did not.

Each baseline is now configured as a competent engineer would deploy it, and executed:
\begin{enumerate}
    \item \textbf{in-toto/DSSE verification} (executed, \texttt{securesystemslib} DSSE PAE + Ed25519): authenticates the envelope against a \emph{pinned trust root} rather than a key travelling with the payload. Blocks \dsseBlocked/\dsseTotal{} (\dssePct\%, CI [\dsseCIlo, \dsseCIhi]).
    \item \textbf{TUF metadata verification} (executed, \texttt{python-tuf}): real Root/Timestamp metadata with \texttt{expires}, signature thresholds and root-driven revocation. Blocks \tufBlocked/\tufTotal{} (\tufPct\%, CI [\tufCIlo, \tufCIhi]).
    \item \textbf{OPA Rego policy} (executed when the \texttt{opa} binary is present; \nolinkurl{governance/baseline_opa.rego}): \opaBlocked/\opaTotal{} (\opaPct\%).
    \item \textbf{Composed pipeline} (DSSE $\wedge$ TUF $\wedge$ OPA): \compBlocked/\compTotal{} (\compPct\%, CI [\compCIlo, \compCIhi]).
    \item \textbf{Unauthenticated status gate}: \cigateBlocked/\cigateTotal{}. Retained explicitly as a \emph{floor}, not a competitor.
\end{enumerate}

The honest headline is therefore \eviBlocked/\eviTotal{} versus \compBlocked/\compTotal{}, and the intervals overlap: with \eviTotal{} vectors this evaluation cannot support a strong quantitative separation, and we do not claim one. What it does support is a \emph{qualitative} account of which vectors survive a modern composed pipeline and why. TUF alone already blocks \tufBlocked{} --- freshness, revocation and threshold signing have been solved since 2010~\cite{samuel2010surviving, kuppusamy2016tuf}, and any paper claiming them as novel for agent releases is mistaken. The composed baseline blocks every authentication, freshness, revocation and policy-threshold vector.

The vectors it does not block are the ones this paper is actually about: V2 and V8 (trace-level integrity --- no baseline recomputes a Merkle root over an action history), V12 (trace-set truncation), V15 and V17 (proof-path and leaf-typing attacks on the audit surface), and V4 (within-gate replay, which requires the verifier to hold state across submissions rather than to validate a document). That is the delta: \emph{binding the release decision to the execution trace, and holding state while deciding}. It is a narrower claim than 100\% versus 30.8\%, and it is one the evaluation can carry.

L3 is the layer whose evaluation we rebuilt. The detector no longer consults any list of anomalous actions. It is fitted on clean profiles alone, learning an action vocabulary, a status vocabulary and a per-action duration envelope, and every anomaly class is held out from that fit. Under this protocol it recalls \insOvertK/\insOvertN{} overt anomalies and \insStealthK/\insStealthN{} stealth anomalies --- overall \insRecallK/\insRecallN{} (\insRecallPct\%, CI [55.4, 76.3]) at \insFPK/\insFPN{} false positives.

The zero is the result. Per-leaf inspection detects agents that do things they have never done before; it is blind to an agent doing a permitted thing for an impermissible reason, which is precisely what a prompt-injected agent looks like in a trace. Combined with L2, the layered picture is: the gate proves what was recorded is genuine, inspection catches structural novelty, and \emph{neither} catches semantically disguised misbehaviour. An earlier revision reported 50/50 recall here. That number was produced by a detector keyed off the same list the corpus generator planted from, and it should not have been reported as a measurement.

\subsection{Deployment Trade-offs}
Two engineering consequences follow from the design. \emph{Audit granularity}: full raw-trace retention at $N=10^6$ needs 220{,}705\,KB per release, while a depth-bound inclusion proof is \sparseProofSizeKb{}\,KB, so organisations can archive raw payloads to cold storage and keep only proofs online. \emph{Replay state}: the gate must hold state across submissions, which is what V16 shows it cannot do across replicas without shared storage; a distributed key-value store with atomic set-if-absent and TTL $\Delta T_{\text{max}}$ is the natural implementation, and the gate must fail closed when that store is unreachable rather than admit a split-brain replay. We have not measured either deployment.

\subsection{Limitations and Threats to Validity}\label{sec:limitations}
\textbf{No real agent executions.} The corpus is synthetic and templated; no LLM agent was run anywhere in this evaluation, and the artifact declares this in its own \texttt{provenance} field. A paper arguing that agent releases need new evidence \emph{because agent behaviour is non-deterministic} should ultimately be evaluated on non-deterministic behaviour. This is the most substantial gap and we do not minimise it.

\textbf{The collector is unimplemented.} Every security guarantee is conditioned on complete mediation at the collection boundary (Definition~\ref{def:completeness}). The production design grounds this at the OS boundary via eBPF; the evaluation uses Python instrumentation wrappers. The load-bearing component is therefore an architectural proposal, not a measured one.

\textbf{The gate does not block semantic misbehaviour, and inspection misses the hard half.} L2 approves all \insRecallN{} anomalous profiles by design; held-out L3 inspection recalls \insStealthK/\insStealthN{} stealth anomalies (Section~\ref{sec:twolayer}). Content-level policy over trace semantics is future work.

\textbf{V16 is unblocked.} Replay protection is a property of gate state. The shipped verifier persists nonces and fails closed when the ledger is unavailable, but cross-replica correctness requires shared storage (Redis/DynamoDB) that the prototype does not implement.

\textbf{Vector-set construct validity.} V1--V12 were authored alongside the checks they exercise and demonstrate only that those checks fire. V14--V18 were authored against the design and three of them broke earlier revisions, which is evidence that the suite has some power --- but a \eviTotal{}-vector suite gives wide intervals (CI [\eviCIlo, \eviCIhi]) and no suite authored by the system's designers can establish resilience to novel attack.

\textbf{Measurement and key management.} Timed figures are means over \benchRepeats{} runs on one platform; $\sigma$ captures within-run noise only. Throughput is measured on three-trace bundles and does not describe large-$N$ verification. Deterministic security results carry no platform dependence. The artifact signs with a static demo key so results reproduce; there is no real KMS round trip, and the 15--25\,ms figure is an estimate.

\textbf{Baseline scope.} DSSE/in-toto and TUF baselines are executed; OPA is executed when the binary is available and declares itself modeled otherwise; the unauthenticated status gate is modeled and reported as a floor, not a competitor.

\section{Related Work}

\textbf{Positioning.} We state the boundary of the claim first: threshold signing, metadata expiry, rollback protection and key revocation are \emph{not} novel here --- TUF has supplied them since 2010~\cite{samuel2010surviving}, and our executed TUF baseline blocks \tufBlocked{} of \tufTotal{} vectors on that basis alone (Section~\ref{sec:comparative}). EviAssure bridges a narrower gap than earlier drafts of this paper claimed: it binds the release decision to a Merkle-attested \emph{execution trace} and holds replay state across submissions, which is what none of the systems below does.

\subsection{Supply Chain Provenance}
in-toto~\cite{torres2019in-toto}, SLSA~\cite{slsa2023supply} and Sigstore/Cosign~\cite{sigstore2022cosign} provide cryptographic provenance for build pipelines and image digests, including vetted runtime-trace predicates~\cite{intoto_runtime_trace}; any release pipeline should use them for the static artifact side. What they do not provide is a stateful authorization layer: freshness windows and replay caches are not integral to step attestations, and release decisions are not bound to attested traces under a pinned policy version. EviAssure supplies that layer while remaining envelope-compatible --- an \texttt{EvidenceBundle} is an in-toto Statement and can carry SLSA provenance, \texttt{agent-decision} records, or custom predicates alongside Merkle-attested traces. Our executed DSSE baseline (Section~\ref{sec:comparative}) quantifies the difference: \dsseBlocked/\dsseTotal{} versus \eviBlocked/\eviTotal{}.

\subsection{Policy Engines, Workload Identity, and Runtime Guardrails}
Policy engines (OPA~\cite{opa2021openpolicy}, Kyverno~\cite{kyverno2022policy}) evaluate declarative rules over admission payloads but compute no Merkle root over an action history and hold no replay state --- our executed OPA baseline blocks \opaBlocked/\opaTotal{}. Workload identity frameworks (SPIFFE/SPIRE~\cite{spiffe2020spire}, Macaroons~\cite{birgisson2014macaroons}) are orthogonal: they establish \emph{who} the runner is, not what action history it produced. Runtime LLM guardrails filter inference-time inputs and outputs; they do not gate the promotion of a checkpoint, prompt template, or tool scope. Update frameworks are the closest prior art on the governance axis: TUF~\cite{samuel2010surviving} and its delegation extensions~\cite{kuppusamy2016tuf, moore2023artemis} already supply expiry, thresholds, rollback and revocation, which is why we execute TUF as a baseline rather than claiming those properties.

\subsection{AI-Agent Provenance and Auditability Standards (2026)}\label{sec:related-2026}
Three recent 2026 initiatives address related challenges in agent provenance, all focusing on record formats rather than active release authorization:

\begin{itemize}
    \item \textbf{in-toto \texttt{agent-decision/v0.1}}~\cite{intoto2026agent-decision}: a May 2026 RFC registering an in-toto predicate for AI-agent policy decisions (identity, principal, evaluated policies, allow/deny outcomes, hashed tool arguments, DSSE-signed). It standardizes the \emph{shape} of a decision record; freshness, replay and revocation remain verifier-side choices.
    \item \textbf{APAS}~\cite{apas2026agent-provenance}: draft provenance chains across agent pipelines, on in-toto Statement envelopes with a \texttt{dispatch} predicate. APAS grades itself: at lower levels provenance is ``self-attested --- an attacker who compromises the orchestrator can forge records.'' EviAssure differs on exactly that axis: signing (KMS/HSM + pinned registry) is separated from recording, so the verdict is reproducible without trusting the orchestrator.
    \item \textbf{AAS-1}~\cite{aas12026agent-audit}: a May 2026 draft evidentiary record format---five record classes, twelve audit assertions, JCS canonicalization, per-issuer hash chains. Those chains let a verifier holding \emph{all} records detect omission between consecutive records; EviAssure makes the binding structural instead, and enforces the authorization semantics audit standards leave to the engagement.
\end{itemize}

\paragraph{Per-action receipt schemes (2026).} A parallel line has converged on having the \emph{receiving} service attest each agent action --- notarized/receiver-attested receipts~\cite{notarized2026agents} and comparable industry proposals~\cite{pipelab2026receipts}. This is the closest prior art to Section~\ref{sec:witness} and we build on it directly: moving attestation out of the agent's trust domain is the right move. Our contribution is what receipts alone cannot give. A receipt certifies that an action \emph{occurred}; a set of receipts does not certify that no \emph{other} action occurred, because an adversary who drops an action drops its receipt and every remaining pair still matches. Sequence-bound receipts plus a signed closing count change that, and Section~\ref{sec:omission} measures the difference: \omReceipts/\omVectors{} against \omWtc/\omVectors{}.

Against all three, EviAssure's contribution is the layer they omit: evidence-bound, fail-closed release \emph{authorization}. Their records ride inside EviAssure's in-toto-compatible envelope unmodified.

\section{Ethics}
All datasets, trace profiles and harnesses are synthetic and locally generated; no human subjects, customer PII, or live credentials are involved, and no measurement touches third-party systems. Dual-use considerations (workplace surveillance, parameter blinding, responsible disclosure) are analysed in Appendix~\ref{sec:appendix_ethics}.

\section{Conclusion}
EviAssure binds a release decision to a domain-separated, depth-bound Merkle attestation of an agent's execution trace, evaluated by a stateful fail-closed gate under a pinned policy. Across \scoredVectors{} adversarial vectors --- five authored independently of the enforcement checks --- it blocks \eviBlocked{} (\eviPct\%, CI [\eviCIlo, \eviCIhi]) against \compBlocked{} for an executed composition of in-toto/DSSE, TUF and OPA, with \falseBlockK/\falseBlockN{} clean controls falsely blocked. It fails one, cross-replica nonce replay, which we report. Held-out inspection over \corpusProfiles{} profiles recalls \insOvertK/\insOvertN{} overt anomalies and \insStealthK/\insStealthN{} semantically disguised ones. That last pair is the honest boundary of the contribution: evidence-bound release assurance makes an unauthorised agent release undeniable and attributable, not impossible.

\section{Ethics and Dual-Use Analysis}\label{sec:appendix_ethics}
The research presented in this paper introduces a defensive mechanism to ensure the security and provenance of autonomous agent releases. This work does not involve human subjects, does not analyze personally identifiable information, and does not conduct active measurements against production systems or networks operated by third parties. The \scoredVectors{} adversarial tamper vectors and the \corpusProfiles{}-profile corpus are fully synthetic and generated within isolated, local test environments for the sole purpose of evaluating the proposed cryptographic and policy enforcement mechanisms. 

\paragraph{Dual-Use Considerations.}
Cryptographic execution attestation mechanisms, if repurposed maliciously, could theoretically be employed to construct invasive employee monitoring frameworks or enforce rigid software lock-in. EviAssure mitigates these dual-use concerns by enforcing decentralized multi-signature threshold governance and open policy schemas (\nolinkurl{governance/release_policy.yaml}), and by keeping raw payloads out of evidence bundles entirely --- traces carry digests only. Salted HMAC blinding (\texttt{blind\_payload}) additionally unlinks the same recorded action across deployments, though as Section~\ref{sec:blind} states, it does not conceal payload equality within one deployment.

\paragraph{Data Privacy \& Parameter Blinding.}
Autonomous software agents frequently process confidential prompt texts, customer financial details, or proprietary source code snippets. To prevent public release audit logs from exposing sensitive data, EviAssure keeps raw payloads out of evidence bundles entirely---traces carry digests only---and the blinding protocol additionally re-keys those digests with a per-deployment salted HMAC ($H_{\text{blinded}}$), so the same recorded action is not linkable across environments. Within one environment the deterministic construction still reveals repetition (Definition 3). This preserves full Merkle tree inclusion auditability without storing proprietary inputs in the audit log.

\paragraph{Responsible Disclosure \& Safety Impact.}
EviAssure raises the cost of forging or replaying release evidence produced by a compromised runner. It does \emph{not} prevent prompt injection: an injected agent produces genuine actions that the collector honestly records and the gate correctly approves, and Section~\ref{sec:twolayer} measures this directly --- all \insRecallN{} anomalous corpus profiles, including the injection class, are APPROVED. The contribution is that such a release becomes \emph{undeniable and attributable} after the fact, not that it is prevented. An earlier version of this appendix claimed prevention; that claim contradicted our own Section~\ref{sec:twolayer} results and has been withdrawn.
