\begin{abstract}
As autonomous agentic AI systems assume critical operational responsibilities---executing software workflows, interacting with financial APIs, and modifying persistent databases---releasing new model checkpoints or expanding tool privilege scopes introduces severe security risks. Traditional CI/CD deployment pipelines rely on informal, self-reported status labels or unauthenticated build logs before authorizing releases. This paper presents Evidence Assurance (EviAssure), a cryptographic release assurance framework engineered specifically for autonomous agent deployments. EviAssure's core contribution is \emph{evidence-bound fail-closed release authorization}: the release decision is a deterministic, auditable function of cryptographically attested execution evidence under a pinned policy version, with freshness, replay, and revocation enforced over the same signed payload. The system contributes (1) an Ed25519 and SHA-256 Merkle tree execution trace attestation engine that seals agent action histories into immutable evidence packs carrying signed trace counts and depth-bound inclusion proofs; (2) an in-toto v0.2 / SLSA v1.0 compatible \texttt{EvidenceBundle} envelope with nonces, timestamps, multi-signature threshold gating, and privacy-preserving salted trace parameter blinding; (3) a fail-closed \texttt{ReleasePolicyEngine} enforcing multi-factor release conditions, KMS key ARN verification, and key revocation list (CRL) validation; and (4) a per-leaf forensic inspection layer that surfaces semantic misbehavior that an integrity-preserving gate cannot reject. Empirical benchmarks demonstrate that EviAssure achieves a 100.0\% fail-closed block rate across 12 attack vectors (versus 0.0\% for standard CI exit-code gates, 25.0\% for an \emph{executed} OPA schema-policy gate, and 25.0\% for a Sigstore/Cosign-style artifact-signature gate) while processing policy gate evaluations at up to \textbf{\peakThroughput{} operations/second} (mean of \benchRepeats{} runs; $\sigma$ recorded in the artifact) and scaling Merkle tree construction for $N=100{,}000$ execution traces in $\merkleBuildMs\text{ ms}$. Like any attested-execution system, EviAssure proves evidence \emph{integrity} (nothing modified what was recorded) unconditionally, while trace \emph{completeness} (everything that occurred was recorded) holds under an explicit trust boundary at the evidence collector; the paper formalizes this distinction in a system-level Release Authorization Soundness theorem and positions the design against in-toto/SLSA and the 2026 agent-provenance and auditability standards.
\end{abstract}

\section{Introduction}
Autonomous software agents driven by Large Language Models (LLMs) operate dynamically across complex tool environments, API endpoints, and persistent memory stores~\cite{yang2024swebench, greshake2023not, yao2023react}. Unlike static software artifacts whose behaviors are deterministically governed by compiled code, autonomous agents exhibit non-deterministic reasoning patterns, dynamic tool execution flows, and adaptive multi-step decision sequences. When deploying agent updates, expanding tool privilege scopes, or promoting agentic pipelines to production, organization-wide security depends upon verifying that safety invariants, authorization constraints, and regression test suites have been rigorously validated~\cite{greshake2023not}.

Existing software delivery and release pipelines suffer from a fundamental trust defect: traditional deployment gates evaluate unauthenticated status signals (such as process exit codes, plain text console logs, or un-signed JSON build status files) generated by intermediate runner environments. An attacker who gains control over an intermediate build step, manipulates agent memory traces, or exploits prompt injection vectors can easily forge release approval signals, bypassing security verification entirely~\cite{torres2019in-toto, slsa2023supply, samuel2010surviving, cappos2008look}.

Empirical studies of the open-source ecosystem confirm both the prevalence and the practical exploitability of these compromise paths: taxonomies of documented supply-chain attacks now enumerate hundreds of real incidents~\cite{ladisa2023sok, okafor2022sok}, large-scale measurement work shows package-manager compromise to be routine in interpreted-language ecosystems~\cite{duan2021towards}, and multi-repository update systems require dedicated defenses~\cite{moore2023artemis}.

To address these critical vulnerabilities, EviAssure introduces an evidence-backed release assurance architecture that replaces informal release signals with cryptographically authenticated Evidence Bundles backed by Merkle inclusion proofs, timestamp freshness windows, Ed25519 digital signatures, KMS key ARNs, and SLSA v1.0 provenance envelopes.

\subsection{Key Contributions}
The primary technical and systems contributions of this work include:
\begin{enumerate}
    \item \textbf{Evidence-Bound Fail-Closed Release Authorization}: The system-level contribution is not a new attestation format but an authorization layer: \texttt{ReleasePolicyEngine} outputs a deterministic, reproducible verdict that is a function of attested evidence under a pinned policy version, so an APPROVED release carries its own security proof and the verdict is auditable post-hoc by recomputation.
    \item \textbf{Cryptographic Trace Attestation Engine}: An Ed25519 public-key signature scheme~\cite{bernstein2012high, boneh2001short} coupled with a SHA-256 Merkle tree aggregation protocol that condenses up to $N=1,000,000$ agent execution traces into one immutable 32-byte root digest, with the signed trace count binding the root to exactly the submitted action set (completeness-carrying binding).
    \item \textbf{Multi-Signature Threshold Gating}: Threshold verification policies (at least $K$ of $M$ authorized signatures) before production deployment authorization.
    \item \textbf{Salted Trace Parameter Blinding}: A salted HMAC blinding mode (\texttt{blind\_payload}) using keyed hashes~\cite{krawczyk1997hmac} that conceals prompt text, API inputs, and PII while preserving public Merkle auditability.
    \item \textbf{Browser DOM \& Visual Attestation}: Execution trace attestation extended to browser UI actions, DOM state hashes ($\text{SHA256}(\text{DOM}_{\text{serialized}})$), and screenshot render-reference digests.
    \item \textbf{System-Level and Primitive-Level Security Proofs}: A sequence-of-games proof reducing tamper-resistance to EUF-CMA and hash collision resistance~\cite{bellare1993random}, together with a system-level \emph{Release Authorization Soundness} theorem (Section~\ref{sec:proofs}) stating what an APPROVED verdict means and the exact trust boundaries (evidence collector, key registry, nonce state) on which that meaning rests.
    \item \textbf{Two-Layer Evidence Model}: Separation of cryptographic \emph{integrity} (enforced by the gate) from per-leaf \emph{semantic inspection} (surfacing recorded actions that should not have occurred), evaluated at corpus scale over 1,050 agent profiles.
    \item \textbf{Corpus \& Forensic Infrastructure}: A 1,050-profile multi-architecture agent trace corpus (\url{corpus/agent_trace_corpus.json}) with 50 anomaly profiles spanning 10 anomaly types, and a CLI forensic inspection tool (\url{scripts/audit_trace_forensics.py}).
    \item \textbf{Empirical Evaluation}: 100.0\% block rate across 12 tamper vectors versus 0.0\% (CI exit-code), 25.0\% (executed OPA schema gate), and 25.0\% (Sigstore-style signature gate), with all timed measurements reported as means over \benchRepeats{} runs.
\end{enumerate}

\paragraph{Positioning.}
in-toto provides signed, tamper-evident attestations of supply-chain steps---including a vetted runtime-trace predicate---and SLSA builds graduated release provenance on top~\cite{torres2019in-toto, slsa2023supply}; in 2026 the envelope ecosystem extended to AI agents via the \texttt{agent-decision/v0.1} predicate RFC~\cite{intoto2026agent-decision}, the Agent Provenance Attestation Standard~\cite{apas2026agent-provenance}, and the Agent Auditability Standard AAS-1~\cite{aas12026agent-audit}. These efforts define \emph{record formats}; none defines an \emph{authorization layer}: a release gate whose verdict is a deterministic function of attested evidence under a pinned policy version, with freshness, replay, and revocation enforced over the same signed payload. Record formats and authorization layers compose rather than compete---EviAssure's \texttt{EvidenceBundle} is an in-toto v0.2 / SLSA v1.0 compatible envelope, so any predicate that fits a Statement can ride on the same evidence pack. What EviAssure adds that no predicate alone provides is (i) completeness-carrying trace binding via the signed trace count, (ii) freshness and replay protection as \emph{integral gate properties} rather than attestation fields a verifier may or may not enforce, (iii) evidence-bound authorization whose decision is reproducible and auditable, and (iv) a two-layer forensic model separating cryptographic integrity from per-leaf semantic inspection. Section~\ref{sec:related-2026} positions EviAssure against these developments in detail.

\section{System Architecture and Threat Model}
This section outlines the architectural foundation of EviAssure, defining its cryptographic boundary, formal security definitions, and threat model for autonomous agent release pipelines.

\subsection{Hardware Enclave \& KMS Boundary}
To defend against local runner compromise, EviAssure roots signing authority within a Hardware Security Module (HSM) or Cloud KMS boundary (\url{kms://aws/arn:aws:kms:us-east-1:000000000000:key/usenix-release-gate}). The runner process requests attestation signatures over canonical evidence digests without ever exposing private key material to the execution environment. The research prototype signs locally with a pinned demo key; production deployments root the private half in the KMS/HSM, and the gate enforces the ARN boundary (\texttt{kms\_key\_arn\_pattern}) at verification time regardless of where signing occurred.

\subsection{Formal Security Definitions}

\begin{definition}[Unforgeability under Chosen Message Attack (EUF-CMA)]
An Evidence Assurance Scheme $\Sigma = (\text{KeyGen}, \text{Package}, \text{Verify})$ is EUF-CMA secure if for all probabilistic polynomial-time adversaries $\mathcal{A}$, the probability that $\mathcal{A}$ outputs a valid pair $(E^*, \sigma^*)$ such that $\text{Verify}(PK, E^*, \sigma^*) = 1$ without $E^*$ having been signed by an honest party holding $SK$ is negligible in security parameter $\lambda$:
\begin{equation}
\text{Pr}[\text{Exp}_{\Sigma, \mathcal{A}}^{\text{euf-cma}}(\lambda) = 1] \le \text{negl}(\lambda)
\end{equation}
\end{definition}

\begin{definition}[Merkle Trace Inclusion Soundness]
For root $R_M$ committed together with its leaf count $N$, and leaf $H_i$, a Merkle proof $\pi_i$ is sound if no computationally bounded adversary can construct $\pi'_i$ for any $H'_i \neq H_i$ --- including internal node digests of the same tree --- such that $\text{VerifyMerkle}(H'_i, \pi'_i, R_M, \lceil\log_2 N\rceil) = 1$, where verification accepts only proof paths of the committed tree depth.
\end{definition}

\begin{definition}[Salted Trace Parameter Blinding Indistinguishability]
A blinded trace record $T_{\text{blinded}}$ produced with uniform salt $S \gets \{0,1\}^\lambda$ satisfies computational indistinguishability: no PPT adversary $\mathcal{A}$ can distinguish $T_{\text{blinded}}$ from a uniformly random bitstring of equal length without knowledge of $S$.
\end{definition}

\begin{definition}[Evidence Integrity]\label{def:integrity}
An evidence pack $(R_M, \sigma, N)$ comprising a Merkle root $R_M$, signature $\sigma$, and signed trace count $N$ provides \emph{evidence integrity} if no probabilistic polynomial-time adversary can produce any $(R'_M, \sigma', N') \neq (R_M, \sigma, N)$ that verifies; equivalently, nothing that was \emph{recorded} can be modified, reordered, inserted, or removed without detection. Integrity is a property of the signed record and is guaranteed by Theorem~\ref{thm:failclosed} below.
\end{definition}

\begin{definition}[Trace Completeness]\label{def:completeness}
Let $E$ be an agent execution and let $\mathcal{C}$ be the evidence collector that observes $E$. A recorded trace set $T = \{T_1, \dots, T_N\}$ is \emph{complete with respect to $E$} if every action of $E$ that $\mathcal{C}$ observed is represented by exactly one $T_i$. Completeness is a property of the \emph{collector}, not of the Merkle tree: the tree attests exactly the leaves it was given, and no downstream check can distinguish an action that was never recorded from one that was honestly absent.
\end{definition}

\subsection{Threat Model, Trust Boundaries, and Adversary Capabilities}\label{sec:threat}
The security model considers a powerful adversary $\mathcal{A}$ attempting to deploy an unapproved, regression-prone, or malicious agent update to production environments~\cite{shostack2014threat, carlini2024poisoning, schuster2021get}. The adversary $\mathcal{A}$ may control intermediate runner environments, network transit layers, or build scripts. 

\paragraph{Trust Model Boundaries.} EviAssure explicitly assumes that the underlying cryptographic primitives (Ed25519 and SHA-256) remain computationally intractable for PPT adversaries, and that the root Cloud KMS / HSM service faithfully enforces identity access control over private signing keys. Physical hardware side-channel attacks on HSM microchips, total subversion of the cloud provider's root KMS master keys, and host OS kernel hypervisor rootkits are explicitly considered out-of-scope for the release gate layer.

We categorize $\mathcal{A}$'s in-scope capabilities into five adversary capability classes:
\begin{itemize}
    \item $\mathbf{\mathcal{A}_1}$ \textbf{(Runner \& Memory Trace Tampering)}: Modifying in-memory agent execution logs, altering action output hashes, or dropping failed execution steps to present a clean trace history. In an agentic setting, an attacker attempting to deploy a compromised model update might suppress execution traces recording unauthorized system shell commands or SQL table drop queries.
    \item $\mathbf{\mathcal{A}_2}$ \textbf{(Network \& Signature Forgery)}: Injecting forged cryptographic signatures, stripping signature fields, or signing evidence payloads with unauthorized key pairs. An adversary controlling a CI builder might strip Ed25519 signatures or sign payloads using arbitrary self-generated keys.
    \item $\mathbf{\mathcal{A}_3}$ \textbf{(Trace Replay \& Time Skew)}: Replaying historical, previously approved evidence bundles from earlier release cycles or injecting post-dated timestamps into the future to bypass validity windows. An attacker who cannot forge signatures might replay an old, benign evidence pack from a previous release to authorize a malicious deployment.
    \item $\mathbf{\mathcal{A}_4}$ \textbf{(Key Revocation \& Governance Bypass)}: Using revoked key IDs listed in the Key Revocation List (CRL) or attempting KMS ARN parameter confusion. If an organization revokes a key following developer credential leaks, $\mathcal{A}$ attempts to use the revoked key before CRL updates propagate.
    \item $\mathbf{\mathcal{A}_5}$ \textbf{(Serialization \& Key Malleability Injection)}: Injecting uncanonicalized JSON key fields or duplicate dictionary keys to exploit parser discrepancies between packager and verifier. By injecting duplicate JSON dictionary keys or non-standard white-spacing, $\mathcal{A}$ attempts to cause signature verification to succeed over one view while policy parsing evaluates another.
\end{itemize}

The release gate enforces a strict zero-trust fail-closed guarantee: any evidence payload matching any of these attack vectors is rejected with exit code 1 (\texttt{BLOCKED}).

\paragraph{Completeness boundary.}
The distinction between Definition~\ref{def:integrity} (evidence integrity) and Definition~\ref{def:completeness} (trace completeness) scopes every security claim in this paper. The cryptographic layer guarantees \emph{integrity of whatever was recorded}: given the recorded sequence $A \to B \to D \to E$, no adversary can silently substitute $A \to B \to C \to D \to E$ or drop a recorded leaf. It cannot prove that an action executed before collection---say $C$---was recorded at all; a Merkle tree attests its leaves, not the world. EviAssure therefore scopes its guarantees to the \emph{collection boundary}: the evidence collector is assumed to observe and record every action of the release execution, and Theorem~\ref{thm:authorization} states this assumption explicitly. An adversary that compromises the recording path \emph{before} collection can omit actions that no signature or Merkle check can expose---the same boundary every attested-execution system faces, and one the 2026 provenance literature reaches independently (APAS requires external witnesses at its top level; AAS-1 detects omission only \emph{between} records one issuer produced)~\cite{apas2026agent-provenance, aas12026agent-audit}. Residual risk is mitigated by collecting evidence at the outermost observable boundary (the tool-execution or gateway layer) and by semantic inspection (Section~\ref{sec:twolayer}), which surfaces recorded actions that should not have occurred. Actions that never reach the collector are out of scope for any release-attestation system.

\section{Cryptographic Evidence Attestation}
EviAssure establishes verifiable release claims by packaging agent action histories into cryptographically attested evidence bundles. This section describes the Merkle tree aggregation protocol, browser DOM attestation, trace parameter blinding, and SLSA v1.0 / in-toto predicate envelopes.

\subsection{Execution Trace \& Browser UI Attestation Schema}
Each execution trace record $T_i$ captures structured action metadata across autonomous agent steps. For API and backend tool calls, $T_i$ records:
\begin{equation}
T_i = (\text{id}_i, \text{agent}_i, \text{action}_i, \text{status}_i, \text{duration}_i, H_{\text{out},i})
\end{equation}
For browser and UI agent steps, EviAssure extends attestation to capture DOM state hashes ($H_{\text{DOM}}$) and visual screenshot render digests ($H_{\text{screen}}$):
\begin{equation}
T_{\text{UI},i} = (\text{id}_i, \text{agent}_i, \text{action}_i, \text{url}_i, \text{elem}_i, H_{\text{DOM},i}, H_{\text{screen},i})
\end{equation}
$H_{\text{DOM}}$ is computed over the serialized DOM state of the rendered page, $H_{\text{DOM},i} = \text{SHA256}(\text{DOM}_{\text{serialized}})$: the specimen serializes the rendered document deterministically before hashing, so identical page states yield identical digests while any mutation (e.g., an injected modal dialog or altered form control) changes the digest. Each trace record produces a canonical leaf digest $H_i = \text{SHA256}(T_i.\text{to\_hash}())$.

\subsection{Salted Trace Parameter Blinding Protocol}
To protect proprietary prompt text, customer PII, or sensitive API parameters during public audit, EviAssure implements a keyed HMAC blinding mode (\texttt{blind\_payload}). Given the trace's output digest $P_i$ and salt $S \gets \{0,1\}^{256}$:
\begin{equation}
H_{\text{blinded},i} = \text{BLINDED-} \parallel \text{HMAC-SHA256}(S, P_i)
\end{equation}
The blinded value retains the full 256-bit HMAC digest, preserving payload-aliasing resistance at the same scale as the underlying hash. It replaces raw payload strings in leaf construction while preserving global Merkle tree inclusion verification.

\subsection{Merkle Trace Aggregation and Sparse Proof Compression}
To attest $N$ execution traces without transmitting full raw logs to every gate request, EviAssure aggregates normalized trace digests into a SHA-256 Merkle tree~\cite{merkle1989digital, laurie2014certificate}. Each trace record $T_i$ maps to leaf digest $H_i$.

For $N=1,000$ traces, transmitting raw trace logs requires 222.6 KB of storage, scaling to 220,705.03 KB for $N=1,000,000$ traces. EviAssure provides sparse Merkle proof compression, transmitting the 32-byte root $R_M$ and $O(\log N)$ inclusion proof paths $\pi_i$ for audited steps. 

Given proof path $\pi_i = \{(P_1, \text{pos}_1), \dots, (P_K, \text{pos}_K)\}$, inclusion is verified recursively by setting $C_0 = \text{SHA256}(H_i)$ and evaluating:
\begin{equation}
C_j = \begin{cases}
\text{SHA256}(C_{j-1} \parallel P_j), & \text{if } \text{pos}_j = \text{right} \\
\text{SHA256}(P_j \parallel C_{j-1}), & \text{if } \text{pos}_j = \text{left}
\end{cases}
\end{equation}
The proof is valid if and only if $C_K = R_M$ and the path length equals the committed tree depth $\lceil\log_2 N\rceil$, derived from the signed execution trace count; the length check prevents internal node digests from being verified as leaves --- a substitution that would otherwise succeed without any hash collision --- reducing transmission size to $<5\text{ KB}$.

\begin{lstlisting}[language=python,caption={Merkle Trace Aggregation Protocol.},label={lst:proto1}]
def build_merkle_tree(traces):
    leaves = [t.to_hash() for t in traces]
    current = leaves
    levels = [leaves]
    while len(current) > 1:
        next_level = []
        for i in range(0, len(current), 2):
            left = current[i]
            right = current[i+1] if i+1 < len(current) else current[i]
            next_level.append(hash_sha256(f"{left}:{right}"))
        current = next_level
        levels.append(current)
    return current[0], levels
\end{lstlisting}

\section{Fail-Closed Policy Verification Engine}
Release authorization in EviAssure is governed by a zero-trust policy engine (\texttt{ReleasePolicyEngine}) that enforces mandatory fail-closed default rules. This section details the declarative policy schema, multi-factor evaluation protocol, key governance rules, and the system-level formal security analysis.

\subsection{Declarative Policy Governance Rules}
A release policy specification $P$ defines strict quantitative safety thresholds and cryptographic verification conditions:
\begin{equation}
\begin{split}
P = (\,P_{\text{min\_pass}},\ &P_{\text{max\_drift}}, P_{\text{min\_sigs}}, P_{\text{valid\_window}},\\
&\mathcal{K}_{\text{trusted}}, \mathcal{K}_{\text{rev}}, \mathcal{A}_{\text{KMS}})
\end{split}
\end{equation}
where:
\begin{itemize}
    \item $P_{\text{min\_pass}}$: Minimum required unit and integration test pass rate (default: $100.0\%$ (100/100)).
    \item $P_{\text{max\_drift}}$: Maximum allowable unresolved security drift findings (default: $0$).
    \item $P_{\text{min\_sigs}}$: Required threshold number of valid signatures from authorized keys (default: $K=1$).
    \item $P_{\text{valid\_window}}$: Evidence timestamp freshness validity window $\Delta T_{\text{max}} = 3,600\text{ s}$ ($1\text{ hour}$) with a maximum future clock skew tolerance of $\delta_{\text{skew}} = 30\text{ s}$.
    \item $\mathcal{K}_{\text{trusted}}$: Trusted key registry pinning authorized signing key IDs to their Ed25519 public keys (\url{governance/trusted_keys.yaml}). Signature verification uses the pinned key, never a public key supplied inside a submitted bundle; unregistered key IDs are rejected. The registry follows the key-accountability patterns of key transparency~\cite{melara2015coniks} and delegation hierarchies~\cite{kuppusamy2016tuf}: verification authority rests on a small, versioned, offline-pinnable root set rather than on keys that travel with the evidence.
    \item $\mathcal{K}_{\text{rev}}$: Key Revocation List (CRL) tracking compromised or deprecated key identifiers.
    \item $\mathcal{A}_{\text{KMS}}$: Required Cloud KMS or HSM key ARN boundary pattern matching.
\end{itemize}

Listing~\ref{lst:proto2} outlines the complete zero-trust verification algorithm enforced by \texttt{ReleasePolicyEngine}.

\begin{lstlisting}[language=python,caption={Fail-Closed Policy Gate Verification Protocol.},label={lst:proto2}]
# Protocol 2: Fail-Closed Policy Gate Verification
# Input: Evidence E, Policy P, Revoked keys K_rev, Seen nonces N_seen
# Output: Decision D in {APPROVED, BLOCKED}
def evaluate_release_gate(E, P, K_rev, N_seen):
    if not E.signed or E.signature is None:
        return BLOCKED, ["POLICY_VIOLATION: Unsigned payload"]
    
    # 1. Signature & Key Governance Verification
    valid_sigs = 0
    for s_entry in E.signatures:
        if s_entry.key_id in K_rev or s_entry.key_id not in K_trusted:
            continue   # revoked or unregistered key
        if s_entry.pub_key != K_trusted[s_entry.key_id]:
            continue   # spoofed key_id under an attacker key
        if s_entry.kms_arn and not match_kms_arn(s_entry.kms_arn, P.kms_pattern):
            continue
        if verify_signature(s_entry):
            valid_sigs += 1
            
    if valid_sigs < P.min_signatures:
        return BLOCKED, ["POLICY_VIOLATION: Insufficient signatures"]
        
    # 2. Merkle Root Integrity Verification
    recalculated_root, _ = build_merkle_tree(E.traces)
    if recalculated_root != E.merkle_root:
        return BLOCKED, ["POLICY_VIOLATION: Merkle root mismatch"]
        
    # 3. Quality & Security Drift Thresholds
    if E.test_pass_pct < P.min_pass_pct:
        return BLOCKED, ["POLICY_VIOLATION: Sub-threshold pass rate"]
    if E.unresolved_drift > P.max_drift:
        return BLOCKED, ["POLICY_VIOLATION: Unresolved drift"]
        
    # 4. Nonce Replay & Freshness Windows
    if E.nonce in N_seen:
        return BLOCKED, ["POLICY_VIOLATION: Replayed nonce"]
    if not is_timestamp_fresh(E.timestamp, P.valid_window, max_skew=30):
        return BLOCKED, ["POLICY_VIOLATION: Timestamp expired/skewed"]
        
    N_seen.add(E.nonce)
    return APPROVED, []
\end{lstlisting}

\subsection{Formal Security Analysis}\label{sec:proofs}

The security analysis proceeds in two layers. Theorem~\ref{thm:failclosed} is the primitive-level argument: a sequence of games showing what no adversary can do to the cryptographic components, reducing to EUF-CMA and collision resistance. Theorem~\ref{thm:authorization} is the system-level argument: it states what an APPROVED verdict \emph{means} --- the actual security objective of a release gate --- and makes explicit the trust boundaries (evidence collector, key registry, nonce state) on which that meaning rests.

\begin{theorem}[Fail-Closed Release Soundness]\label{thm:failclosed}
Under the assumption that Ed25519 signatures are EUF-CMA secure and SHA-256 is collision-resistant, no probabilistic polynomial-time adversary $\mathcal{A}$ can induce \texttt{ReleasePolicyEngine} to output $\text{APPROVED}$ for a modified trace history, forged signature, replayed nonce, or non-compliant evidence payload except with negligible probability $\text{negl}(\lambda)$.
\end{theorem}

\begin{proof}
The proof structures the security argument using a formal sequence of games $\text{Game}_0 \to \text{Game}_1 \to \text{Game}_2 \to \text{Game}_3 \to \text{Game}_4$:
\begin{itemize}
    \item $\mathbf{Game}_0$: Standard execution of adversary $\mathcal{A}$ interacting with an honest evidence packager and policy gate verifier.
    \item $\mathbf{Game}_1$: Identical to $\text{Game}_0$, except the verifier aborts if $\mathcal{A}$ produces a valid signature $\sigma^*$ over a forged payload $E^*$ under key $PK$ without $SK$. The probability of $\mathcal{A}$ distinguishing $\text{Game}_0$ from $\text{Game}_1$ is bounded by the EUF-CMA security of Ed25519:
    \begin{equation}
    |\text{Pr}[G_0] - \text{Pr}[G_1]| \le \text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A})
    \end{equation}
    \item $\mathbf{Game}_2$: Identical to $\text{Game}_1$, except the verifier aborts if $\mathcal{A}$ produces a trace set $\mathcal{T}^* \neq \mathcal{T}$ such that $\text{MerkleRoot}(\mathcal{T}^*) = R_M$. The verifier additionally binds the claimed trace count to the recomputed tree and inclusion proofs to the committed depth, so internal-node substitution itself requires a collision. The difference between $\text{Game}_1$ and $\text{Game}_2$ is bounded by the collision resistance of SHA-256:
    \begin{equation}
    |\text{Pr}[G_1] - \text{Pr}[G_2]| \le \text{Adv}_{\text{SHA256}}^{\text{coll}}(\mathcal{A})
    \end{equation}
    \item $\mathbf{Game}_3$: Identical to $\text{Game}_2$, except the verifier aborts if $\mathcal{A}$ submits a replayed evidence nonce $N^* \in N_{\text{seen}}$. Nonces are recorded in the state memory $N_{\text{seen}}$ over the validity window, so the probability of within-window reuse acceptance in $\text{Game}_3$ is identically zero; replays after expiry are rejected by the freshness check of $\text{Game}_0$'s policy evaluation.
    \item $\mathbf{Game}_4$: Identical to $\text{Game}_3$, except the verifier aborts if $\mathcal{A}$ uses a revoked key $K^* \in \mathcal{K}_{\text{rev}}$ or an out-of-bounds KMS ARN. Rejection in $\text{Game}_4$ is deterministic.
\end{itemize}
Combining the game hops, the total advantage of adversary $\mathcal{A}$ is strictly bounded:
\begin{equation}
\begin{split}
\text{Adv}_{\text{EviAssure}}^{\text{tamper}}(\mathcal{A}) &\le \text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A}) + \text{Adv}_{\text{SHA256}}^{\text{coll}}(\mathcal{A}) \\
&\le \text{negl}(\lambda)
\end{split}
\end{equation}
This completes the proof.
\end{proof}

Theorem~\ref{thm:failclosed} bounds an adversary's ability to \emph{fake} evidence; it says nothing on its own about what a genuine, honestly-signed evidence pack entitles its holder to. That is the release-gate question, and it is Theorem~\ref{thm:authorization}.

\begin{theorem}[Evidence-Bound Release Authorization Soundness]\label{thm:authorization}
Fix a policy version $P$ and a trusted key registry $\mathcal{K}_{\text{trusted}}$. If \texttt{ReleasePolicyEngine} outputs $\text{APPROVED}$ for evidence $E$, then, except with probability $\text{negl}(\lambda)$, all of the following hold:
\begin{enumerate}
    \item[(i)] \textbf{Authenticity:} $E$ carries a valid Ed25519 signature by a non-revoked key pinned in $\mathcal{K}_{\text{trusted}}$; attacker-generated keys, spoofed key IDs, and revoked keys cannot produce a valid signature.
    \item[(ii)] \textbf{Evidence binding:} the recomputed Merkle root over the submitted trace set equals the signed root, the signed trace count equals the number of submitted traces, and every inclusion proof binds to the committed tree depth; the recorded evidence therefore corresponds exactly to what was submitted.
    \item[(iii)] \textbf{Freshness:} the timestamp lies within the validity window $\Delta T_{\text{max}}$ and the skew bound $\delta_{\text{skew}}$, and the nonce has not been processed within the window; the release is not a replay of an earlier approved bundle.
    \item[(iv)] \textbf{Policy compliance:} all declared thresholds (test pass rate, unresolved drift, KMS ARN boundary, signature threshold $K$) satisfy policy version $P$; an APPROVED verdict under a different policy version is not an APPROVED verdict for this release.
\end{enumerate}
The guarantees hold conditionally on (a) the \emph{collector assumption} of Definition~\ref{def:completeness} --- the evidence collector observed and recorded every action of the release execution --- which supplies the completeness half of the guarantee, and (b) the \emph{key-management assumption} --- registry keys are honestly generated and the HSM/KMS enforces the ARN boundary. The theorem asserts nothing about actions that never reached the collector, nor about the semantic correctness of recorded trace content; both are scoped in Section~\ref{sec:threat} and handled by the inspection layer (Section~\ref{sec:twolayer}).
\end{theorem}

\begin{proof}
\textbf{(i)} Follows from Theorem~\ref{thm:failclosed}, Game$_1$, plus the deterministic registry checks enforced before any signature verification (\texttt{policy.py}): unknown key IDs, bundle-supplied keys disagreeing with the registry, and revoked keys are rejected outright, so per-signature success is bounded by $\text{Adv}_{\text{Ed25519}}^{\text{euf-cma}}(\mathcal{A})$. \textbf{(ii)} Follows from Theorem~\ref{thm:failclosed}, Game$_2$, plus the deterministic signed-count check $N = |\text{traces}|$; substitution requires either a hash collision or a broken signature. \textbf{(iii)} Freshness, skew, and nonce checks are deterministic (Game$_3$; Listing~\ref{lst:proto2}) and hold with probability $1$ given correct gate state, with the disclosed caveat that replay protection requires sharing the nonce cache across gate replicas (Section~\ref{sec:limitations}). \textbf{(iv)} Threshold comparisons are deterministic over the signed payload and the pinned policy version. Composition yields the statement; the only probabilistic terms reduce to the primitive advantages of Theorem~\ref{thm:failclosed}.
\end{proof}

\section{Real-World Case Study and Production CI/CD Integration}
To evaluate operational deployment feasibility, EviAssure was integrated into a production CI/CD workflow. This section presents the GitHub Action architecture, browser UI attestation runner, and the 1,050-profile agent execution trace corpus.

EviAssure was deployed as a production GitHub Action (\url{.github/actions/evidence-release-gate/action.yml}) and an in-toto v0.2 layout specification (\url{governance/intoto_layout.json}). Evaluation tested two primary agentic workflow specimens:
\begin{enumerate}
    \item \textbf{Backend Multi-Step Workflow Specimen} (\url{specimens/agent_runner.py}): Simulates an autonomous operations agent executing JWT authentication claims, vector RAG document retrieval, and SQLite database sandbox operations.
    \item \textbf{Browser UI Action Specimen} (\url{specimens/web_app_runner.py}): Simulates a web-browser autonomous agent executing page navigation, button clicks, DOM state hashing ($\text{SHA256}(\text{DOM}_{\text{serialized}})$), and screenshot render-reference digests ($\text{SHA256}(\text{render})$).
\end{enumerate}

\subsection{Production GitHub Action Architecture}
The production GitHub Action workflow integrates directly into automated PR check steps and production deployment pipelines:
\begin{enumerate}
    \item \textbf{Environment Initialization}: Loads public key registries, Key Revocation Lists ($\mathcal{K}_{\text{rev}}$), and policy files (\url{governance/release_policy.yaml}).
    \item \textbf{Evidence Pack Ingestion}: Consumes the generated \texttt{EvidenceBundle} output by the agent runner specimen.
    \item \textbf{Zero-Trust Gate Execution}: Executes \texttt{ReleasePolicyEngine} (\url{scripts/verify_release_gate.py}). If verification fails, the action logs violation messages, outputs structured diagnostic JSON, and exits with code 1 (\texttt{BLOCKED}).
    \item \textbf{Pipeline Authorization}: Upon successful policy verification, the action exports SLSA Provenance v1.0 statements and authorizes downstream deployment jobs.
\end{enumerate}

\subsection{Expanded Agent Execution Trace Corpus (\texorpdfstring{$N=1,050$}{N=1,050})}\label{sec:corpus}
A 1,050-profile benchmark corpus (\url{corpus/agent_trace_corpus.json}) was constructed across five agent architectures (CodeSynthesisAgent, MultiStepRAGAgent, DatabaseAdminAgent, FinancialAPIIntegratorAgent, AutonomousWebScraperAgent): 1,000 clean profiles and 50 anomalous profiles spanning 10 planted anomaly types (indirect prompt injection, privilege escalation, unauthorized shell spawning, database drops, secret exfiltration, memory trace tampering, SSRF, vector store poisoning, un-sandboxed process creation, JSON key malleability) at five profiles per type. Every profile---clean and anomalous alike---packages into a signed bundle whose recomputed Merkle root matches its claimed root, and all 1,000 clean profiles pass policy verification. The planted anomalies are semantic (visible in trace status fields) rather than cryptographic: because anomalous profiles remain well-formed signed bundles, they surface through per-leaf forensic inspection (Section~\ref{sec:forensics}) instead of the cryptographic gate, whose blocking behavior is measured over the 12 tamper vectors (Section~\ref{sec:tamper}) and whose two-layer behavior over the full corpus is measured in Section~\ref{sec:twolayer}.

\subsection{CLI Forensic Inspection \& Audit Tool}\label{sec:forensics}
To assist security incident response teams during post-incident investigations, EviAssure provides an offline forensic inspection utility (\url{scripts/audit_trace_forensics.py}). The forensic tool parses serialized \texttt{EvidenceBundle} files, reconstructs the full Merkle tree, verifies Ed25519 public key signatures against trusted CRL stores, and isolates specific leaf index anomalies. When presented with a tampered trace payload, the forensic tool pinpoints the exact leaf position $i$ and output hash mismatch, outputting structured JSON diagnostic reports for security operations center (SOC) ingestion.

\subsection{Sparse Merkle Inclusion Proof Compression \& Audit Latency}
In enterprise release auditing, security reviewers frequently require verification of individual high-risk agent steps (e.g., database schema alterations or financial API calls) without re-processing full trace logs (220,705 KB at $N=1{,}000{,}000$). EviAssure's $O(\log N)$ sparse Merkle inclusion proof generator extracts compact verification paths for target leaf indices. For $N=1,000,000$ traces (tree depth 21), proof path generation requires $\sparseProofGenMs\text{ ms}$ (mean over \benchRepeats{} runs), yielding a \sparseProofSizeKb{} KB proof payload containing \sparseProofNodes{} SHA-256 node digests. Inclusion verification against root $R_M$ requires $\sparseProofVerifyMs\text{ ms}$, a bandwidth reduction exceeding $99.99\%$ compared to full log transmission (\sparseProofSizeKb{} KB vs.\ 220,705 KB).

\subsection{Salted Trace Parameter Blinding Performance}
To evaluate the runtime overhead of privacy-preserving parameter blinding (\texttt{blind\_payload}), 10,000 execution traces containing sensitive prompt texts and PII strings were processed using keyed HMAC-SHA256 hashes with a 256-bit salt over \benchRepeats{} runs. Parameter blinding added $\blindingPerRecordMs\text{ ms}$ of latency per trace record ($\blindingTotalMs\text{ ms}$ total for $N=10,000$), demonstrating that privacy protection imposes negligible performance overhead.

\subsection{Browser UI DOM State \& Screenshot Render Attestation}
Browser agent UI action attestation was evaluated across 1,000 automated web interaction steps using \texttt{WebBrowserAgentSpecimen}. SHA-256 hashing of the serialized DOM state averaged $\domHashMs\text{ ms}$ per step, and the screenshot render-reference digest ($\text{SHA256}(\text{render})$) averaged $\shotDigestMs\text{ ms}$ per step. When an adversarial DOM mutation (e.g., injecting an unauthorized modal dialog) is introduced, the altered page state changes $H_{\text{DOM}}$ and thus the leaf digest, and the resulting Merkle root mismatch triggers immediate fail-closed gate rejection (\texttt{BLOCKED}).

\subsection{Discussion and Operational Deployment Trade-offs}
Deploying EviAssure in production software engineering organizations involves balancing trade-offs between storage bandwidth, hardware enclave latencies, and nonce cache state management:

\begin{enumerate}
    \item \textbf{Storage vs. Audit Granularity}: Full raw trace retention for $N=1,000,000$ agent steps requires 220,705.03 KB per release. EviAssure's $O(\log N)$ sparse Merkle proof generator transmits \sparseProofSizeKb{} KB proof paths ($\sim 99.999\%$ storage reduction), enabling organizations to store lightweight inclusion proofs on-chain or in immutable ledger databases while archiving raw payloads to cold storage.
    \item \textbf{Hardware Security Enclave Overhead}: Offloading Ed25519 signature generation to Cloud KMS or HSM endpoints introduces an additional network round-trip ($\approx 12\text{--}25\text{ ms}$ per signature call). To prevent CI pipeline bottlenecks, EviAssure batches evidence root digests into multi-signature calls or employs local worker process pools.
    \item \textbf{Stateful Nonce Cache Memory Footprint}: Replay protection requires the verifier engine to maintain a memory cache of active nonces $N_{\text{seen}}$ over the validity window $\Delta T_{\text{max}} = 3,600\text{ s}$. At a rate of 1,000 releases per second, storing $3.6 \times 10^6$ UUID nonces requires approximately 115 MB of RAM, representing a modest memory footprint for enterprise gateway nodes.
\end{enumerate}

\subsection{Limitations and Threats to Validity}\label{sec:limitations}
\textbf{Measurement methodology.} All timed figures are means over \benchRepeats{} runs with standard deviations recorded in the artifact; the repeats are not independent draws across machines or days, so the reported $\sigma$ captures within-run noise only, and run-to-run variation on the order of a few percent across sessions should be assumed. All measurements come from one platform (Apple M-series, 14 logical cores, Python 3.14.x, recorded in the artifact's \texttt{platform} block); cross-platform behavior was not measured. \textbf{Key management.} The artifact signs with a static demo key pinned in \texttt{governance/trusted\_keys.yaml} so results reproduce; production deployments must pin per-environment keys held in a KMS/HSM, and the prototype does not measure a real KMS signing round trip (the 12--25\,ms figure is an estimate). \textbf{Baseline realism.} The OPA baseline is executed (OPA 1.19.0, Rego policy in the artifact); the CI and Sigstore/Cosign baselines are modeled abstractions, as disclosed in Section~\ref{sec:comparative}. \textbf{Completeness boundary.} The security theorems hold for actions the evidence collector observed; an adversary that controls the recording path before collection can omit actions, and no cryptographic check can expose the omission (Sections~\ref{sec:threat} and~\ref{thm:authorization}). \textbf{Scope of blocking.} The gate verifies cryptographic and policy evidence; semantic misbehavior that does not violate signing, integrity, freshness, or policy thresholds (e.g., a well-signed bundle recording unauthorized actions) is surfaced by per-leaf forensic inspection rather than blocked at the gate --- content-level policy over trace semantics is future work, and the corpus evaluation (Section~\ref{sec:twolayer}) reports the inspection layer's 50/50 recall and 0/1000 false-positive rate on the planted anomalies. Replay state ($N_{\text{seen}}$) is process-local: a gate restart resets it within the validity window, so deployments must share nonce state across replicas to preserve replay protection. \textbf{Construct validity.} The 12 vectors were authored by the authors to exercise each enforcement check; a 100\% block rate (12/12 vectors) demonstrates the checks fire, not resilience to novel attacks. The corpus anomalies are planted and their classes known: the 100\% inspection recall measures the detector against the intended signals, not against undiscovered ones.

\subsection{Software Supply Chain Security Frameworks}
Software supply chain security frameworks such as in-toto~\cite{torres2019in-toto}, SLSA~\cite{slsa2023supply}, and Sigstore/Cosign~\cite{sigstore2022cosign} provide cryptographic provenance for static build pipelines and container image digests. In-toto records step-level layout attestations, and its attestation framework ships vetted predicates including runtime traces, test results, and SCAI evidence; SLSA builds four graduated levels of build-environment isolation on top. These systems attest \emph{what happened} in a build, and any release pipeline should leverage them for the artifact half of the story. What they do not provide is an authorization layer for agent releases: no freshness window or replay cache is integral to step attestations (a verifier may enforce or ignore them), no release decision is bound to the attested evidence under a pinned policy version, and non-deterministic multi-step LLM agent traces, browser DOM mutations, and salted blinding have no native representation. EviAssure supplies that missing half while remaining envelope-compatible: its \texttt{EvidenceBundle} is an in-toto Statement that can carry SLSA provenance, an \texttt{agent-decision}, or any other predicate alongside the Merkle-attested trace pack (Section~\ref{sec:related-2026}).

\subsection{Policy Gate Engines \& Admission Controllers}
General-purpose policy engines such as Open Policy Agent (OPA)~\cite{opa2021openpolicy} and Kyverno~\cite{kyverno2022policy} evaluate declarative Rego or YAML policy rules over JSON admission requests. While effective for Kubernetes cluster governance, OPA and Kyverno do not compute Merkle inclusion roots over action histories, nor do they maintain stateful nonce replay caches or key revocation list (CRL) validation out-of-the-box. As demonstrated in our comparative empirical benchmarks, evaluating unauthenticated admission payloads without trace attestation leaves gates vulnerable to trace tampering and replay attacks.

\subsection{Dynamic Capability \& Workload Identity Tokens}
Authorization frameworks such as Macaroons~\cite{birgisson2014macaroons} and SPIFFE/SPIRE~\cite{spiffe2020spire} provide cryptographic capability tokens with contextual caveats and short-lived X.509 workload identities. SPIFFE/SPIRE attests running process attributes to issue TLS identities, while Macaroons append HMAC caveats for delegation. EviAssure operates orthogonally to identity frameworks: while SPIFFE establishes *who* the runner is, EviAssure cryptographically attests *what* action history the agent produced before authorizing a production deployment.

\subsection{Runtime LLM Guardrails vs. Release Assurance}
Runtime LLM guardrail platforms (e.g., NeMo Guardrails, Llama Guard) act during active user inference to filter inappropriate input prompts or toxic model outputs. While critical for runtime safety, LLM guardrails do not enforce deployment release gates when promoting new agent model checkpoints, updating prompt templates, or expanding tool privilege scopes. EviAssure complements runtime guardrail systems by establishing a cryptographically attested, fail-closed release gate for pre-deployment validation~\cite{slsa2023supply}.

\subsection{AI-Agent Provenance and Auditability Standards (2026)}\label{sec:related-2026}
The research landscape moved in 2026; three developments are closest to EviAssure's territory, and all three are \emph{record-format} efforts rather than authorization layers:

\begin{itemize}
    \item \textbf{in-toto \texttt{agent-decision/v0.1} predicate}~\cite{intoto2026agent-decision}: a May 2026 RFC proposes registering an in-toto predicate for AI-agent policy decisions---agent identity, principal, evaluated policies, allow/deny outcomes, hashed tool arguments, timestamps, and trace correlation, signed with Ed25519 DSSE. It standardizes the \emph{shape} of a decision record; it does not enforce a release decision, and freshness, replay, and revocation remain verifier-side choices.
    \item \textbf{Agent Provenance Attestation Standard (APAS)}~\cite{apas2026agent-provenance}: a draft standard for cryptographically verifiable provenance chains across autonomous agent pipelines (work decomposition $\rightarrow$ execution $\rightarrow$ code delivery), built on in-toto Statement envelopes with a \texttt{dispatch} predicate. APAS grades itself: at lower levels provenance is ``self-attested --- an attacker who compromises the orchestrator can forge records,'' and external witnessing is deferred to its top level. EviAssure's layout differs on the axis APAS itself flags: signing (KMS/HSM + pinned registry) is separated from recording, and the release decision is reproducible by an independent verifier without trusting the orchestrator's attestations alone.
    \item \textbf{Agent Auditability Standard (AAS-1)}~\cite{aas12026agent-audit}: a May 2026 draft defining an evidentiary record format for agent activity---five record classes, twelve audit assertions, JCS canonicalization, and per-issuer hash chains. Its hash chains let a verifier holding all records detect omission \emph{between} consecutive records of one issuer; EviAssure makes the analogous binding structural rather than optional---the signed trace count ties the Merkle root to exactly the submitted action set---and additionally enforces the authorization semantics (freshness, replay, revocation, thresholds) that audit standards deliberately leave to the engagement.
\end{itemize}

Against all three, EviAssure's contribution is the layer they omit: \emph{evidence-bound, fail-closed release authorization}. Their records ride inside EviAssure's in-toto-compatible envelope without modification, and EviAssure's verification approach (pinned keys, signed counts, gate-stateful replay protection) applies to any predicate that fits a Statement. \section{Ethics and Dual-Use Analysis}
This research addresses release assurance infrastructure for autonomous AI agents. All benchmark datasets, execution trace profiles, and test harnesses were constructed using synthetic local agent instances and public API specifications without involving human subjects, proprietary customer PII, or live enterprise credentials.

\subsection{Dual-Use Considerations}
Cryptographic execution attestation mechanisms, if repurposed maliciously, could theoretically be employed to construct invasive employee monitoring frameworks or enforce rigid software lock-in. EviAssure mitigates these dual-use concerns by enforcing decentralized multi-signature threshold governance, open policy schemas (\url{governance/release_policy.yaml}), and client-side salted HMAC parameter blinding (\texttt{blind\_payload}). Blinding ensures that operational safety verification remains decoupled from intrusive payload inspection.

\subsection{Data Privacy \& Parameter Blinding}
Autonomous software agents frequently process confidential prompt texts, customer financial details, or proprietary source code snippets. To prevent public release audit logs from exposing sensitive data, EviAssure's parameter blinding protocol conceals raw payloads behind salted HMAC-SHA256 digests ($H_{\text{blinded}}$). This cryptographic isolation guarantees full Merkle tree inclusion auditability without leaking proprietary inputs.

\subsection{Responsible Disclosure \& Safety Impact}
By enforcing a strict zero-trust fail-closed release gate, EviAssure provides immediate security benefits for organizations deploying autonomous agents into production. It prevents compromised runner environments or indirect prompt injection vulnerabilities from bypassing deployment safety gates, thereby reducing the systemic risk of unauthorized AI agent deployments in critical infrastructure.

\section{Conclusion}
This paper presented EviAssure, a fail-closed evidence-backed release assurance architecture for autonomous agent deployments. By coupling SHA-256 Merkle trace attestation with Ed25519 digital signatures, signed trace-count binding, and zero-trust policy verification, EviAssure replaces unauthenticated release signals with evidence-bound authorization: an APPROVED verdict is a deterministic, auditable function of attested evidence under a pinned policy version. A system-level Release Authorization Soundness theorem states what that verdict means and the trust boundaries it rests on---most importantly the explicit distinction between evidence integrity, which the cryptographic layer guarantees, and trace completeness, which holds at the evidence collector's observation boundary. The empirical evaluation confirms a 100.0\% (12/12) block rate across 12 tamper vectors (versus 0/12 for CI exit-code gates, 3/12 for an executed OPA schema gate, and 3/12 for a Sigstore-style signature gate), and a corpus-scale two-layer evaluation in which 1,050/1,050 profiles attest with valid inclusion proofs, 1,000/1,000 clean profiles pass the gate, and 50/50 planted anomalies are surfaced by per-leaf inspection with zero false positives. Positioned against the 2026 agent-provenance and auditability standards, EviAssure supplies the authorization layer those record formats omit, and remains envelope-compatible so the two compose.
