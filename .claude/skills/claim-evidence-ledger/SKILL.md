# Claim–evidence ledger

A paper is a set of claims. Each claim either traces to evidence or it does not.
The ledger makes that binary and visible. Most "the reviewer found an error"
incidents are not fraud or incompetence — they are a number that was correct in
round three of the experiments and never updated after round four.

## Build the ledger

One row per empirical assertion. A row is complete only when every column is
filled from something you actually opened:

| Column | What goes in it |
|---|---|
| Claim | The sentence as written, quoted |
| Location | file:line, and the section |
| Value | The number, unit, and precision as printed |
| Artifact | Path to the file holding that value |
| Key | The JSON path, CSV cell, or variable inside it |
| Producer | The script that wrote the artifact |
| Command | The exact invocation that regenerates it |
| Status | VERIFIED / DRIFTED / UNSOURCED / DERIVED |

Start from the abstract and introduction. Those carry the claims a reviewer
tests first and are the most likely to be stale, because they are written early
and revised least.

## Status definitions

**VERIFIED** — the value appears in the artifact, at the stated precision,
and you found it there yourself.

**DERIVED** — not stored directly but computed from stored values. Record the
computation. Then *do* the computation and confirm it. Derived values are where
denominators go wrong.

**DRIFTED** — an artifact holds a value close to but not equal to the paper's.
This is the dangerous one. Do not resolve it by editing the paper to match the
artifact. Determine which is current: check file modification times, check
whether the producing script changed, re-run it if you can. A drifted number
often means a whole table is stale, not one cell.

**UNSOURCED** — no artifact contains this value. Three possibilities, and you
must say which: it was computed by hand and never persisted; it came from a run
whose output was lost; or it is wrong. All three block publication. The remedy
is to make the producer emit it, not to delete the check.

## Then audit the aggregation

Values being present is necessary, not sufficient. The errors that survive a
naive ledger:

- **Wrong denominator.** A rate over attempted trials versus completed trials
  versus successful trials. State which, in the paper.
- **Mean of means.** Averaging per-group means when groups have unequal n gives
  a different answer than pooling. Check which the code did and which the claim
  needs.
- **Asymmetric filtering.** An exclusion applied to the treatment arm and not
  the control, usually via a code path that looks innocent.
- **Silent drops.** Timeouts, crashes, and parse failures excluded from the
  denominator without being reported. Count them; report them.
- **Precision inflation.** Reporting 62.47% from n=50 implies a resolution the
  data does not have. Round to what n supports.
- **Unit drift.** ms versus s, MB versus MiB, per-second versus per-minute —
  especially across a table where different rows came from different scripts.

## What to produce

For each defective row: the claim, the correct value with its artifact path, the
direction the correction moves the conclusion, and whether the paper's central
claim survives it. That last sentence is the most valuable thing in the audit.

If a correction would weaken a headline result, say so plainly and early. A
reviewer who finds it first is a rejection; an author who finds it first is a
revision.

## Do not

- Do not edit a number in the manuscript to make a check pass. Propose the
  change, cite the artifact, and let a human accept it. A gate you can silence
  by editing the thing it checks is not a gate.
- Do not mark a row VERIFIED from memory of having seen the file. Open it.
- Do not treat a matching value as a verified claim. The number can be right and
  the sentence around it still overstate what it shows.

## Making drift structurally impossible

The durable fix is to stop transcribing. Have the analysis emit a metrics file
the manuscript includes directly:

```latex
% generated by scripts/freeze_metrics.py — do not edit by hand
\newcommand{\detectionRate}{87.3}
\newcommand{\detectionN}{412}
```

```latex
Our detector flags \detectionRate\% of injections ($n=\detectionN$).
```

Numbers can then be wrong only if the experiment is wrong, which is the failure
mode you can actually detect by re-running.
